# Section 1: Introduction

---

## 1.1 System Overview

The **MHS Marketing Dashboard** is a centralised, web-based marketing intelligence platform built for My Health School (MHS). It consolidates paid advertising performance, organic content analytics, lead management, and AI-powered marketing insights into a single unified interface.

The primary purpose of the dashboard is to give the MHS marketing team real-time visibility into the full acquisition funnel â€” from first ad impression through to paid conversion â€” across every channel the organisation operates: Meta (Facebook and Instagram) paid advertising, organic social content, Wix website analytics, and YouTube advertising. By aggregating data from these channels, and combining it with automated lead synchronisation, revenue tracking via Google Sheets, and AI analysis via Google Gemini, the dashboard enables data-driven decisions on budget allocation, creative strategy, audience targeting, and lead follow-up.

The dashboard is the operational centre for the following activities:

1. Monitoring and analysing Meta Ads performance (spend, leads, CPL, ROAS, Hook Rate, Hold Rate, conversions).
2. Reviewing organic content performance across Instagram and Facebook pages.
3. Tracking Wix website sessions, form submissions, and visitor behaviour.
4. Managing, searching, and exporting leads generated through Meta lead forms.
5. Identifying the best-performing ads and reels by creative metric and revenue impact.
6. Receiving AI-generated strategic recommendations, saturation alerts, fatigue scores, and lead quality scores.
7. Managing dashboard users, roles, and access permissions.

---

## 1.2 System Architecture

The MHS Marketing Dashboard is composed of five integrated layers.

### 1.2.1 Frontend Application

The user interface is a single-page application (SPA) built with **React** (JavaScript). It uses **React Router** for client-side navigation, meaning all page transitions happen without a full browser reload. The application is served from a web host and is accessible from any modern browser. The frontend communicates with the backend exclusively via a REST API, passing a JSON Web Token (JWT) as a Bearer token on every authenticated request.

### 1.2.2 Backend Server

The backend is a **Node.js** application using the **Express** framework. It acts as a secure intermediary between the frontend and all external data sources. All sensitive credentials (Meta access tokens, Google Sheets keys, Wix tokens, Gemini API keys) are held exclusively on the server and are never exposed to the browser. The backend handles:

1. User authentication (login, signup, session validation via `/api/auth/` routes).
2. Proxying requests to the Meta Graph API and formatting responses for the dashboard.
3. Scheduled background synchronisation of leads, insights, and content snapshots.
4. Revenue data retrieval and merging from Google Sheets.
5. AI analysis requests to the Google Gemini API.
6. Wix analytics retrieval and integration with Meta data rows.

### 1.2.3 Database

The dashboard uses two complementary data stores:

1. **PostgreSQL** â€” the primary relational database used for storing synchronised leads, campaign data, and sync-state records. Leads fetched from Meta are written into this database and served to the frontend to avoid repeated live API calls.
2. **Supabase** â€” used as a cloud-hosted PostgreSQL layer, particularly for storing Instagram Stories snapshots generated by the scheduled sync job. Supabase is the persistence layer for content that expires on Meta's API (such as Stories, which are only accessible for approximately 24 hours after posting).

### 1.2.4 External API Integrations

The dashboard integrates with the following external platforms:

1. **Meta Graph API (Facebook and Instagram)** â€” the primary data source for paid advertising metrics (spend, impressions, clicks, leads, CPL, ROAS, Hook Rate, Hold Rate), organic page insights (views, interactions, reach, followers), Instagram Reel performance, lead form data, and audience demographics. All Meta API calls are authenticated using a Meta User Access Token configured in the server environment.
2. **Wix Analytics API** â€” provides website session data, unique visitors, form views, form submissions, and lead counts for the MHS Wix website. Wix analytics data is available for a maximum of 62 days and is merged with Meta data rows in the Ads Analytics Dashboard.
3. **Google Sheets API** â€” used as the authoritative revenue data source. The dashboard polls Google Sheets every 30 seconds to retrieve Online Conversion, Offline Conversion, L1 Revenue, L2 Revenue, and Total Revenue figures for the Ads Analytics section. A separate Google Sheets endpoint provides organic revenue data for the Content Marketing section.
4. **YouTube / Google Ads API** â€” provides YouTube advertising metrics (Cost, Conversions, CPL, CPM, Opt-in Rate, Link Clicks, CTR, ROAS) when the YouTube platform filter is selected in the Ads Analytics Dashboard.
5. **Google Gemini AI API** â€” powers the AI Insights page. The Gemini model receives structured marketing data from the backend and returns lead saturation analysis, creative fatigue scoring, lead quality scoring, strategic recommendations, and natural-language responses to user-typed questions via the Ask AI interface.

### 1.2.5 Background Scheduler

Several automated processes run in the background on the server without requiring any user action. These ensure that lead data, content snapshots, and insights are kept current:

1. **Leads Synchronisation (every 5 minutes)** â€” the server automatically fetches new leads from all connected Meta pages and writes them into the PostgreSQL database. This ensures the lead tables in the dashboard reflect near-real-time data. Users can also trigger an immediate on-demand sync using the "Sync All Leads" button on the Dashboards page.
2. **Ads Insights Sync** â€” campaign and ad performance metrics are cached from the Meta API on a scheduled basis to reduce live API load and ensure fast dashboard load times. Users can force a live refresh using the "Refresh with live data" button.
3. **Instagram Stories Snapshot Sync** â€” because Instagram Stories expire after approximately 24 hours on the Meta API, a scheduled job captures story-level metrics (views, likes, comments, shares) at regular intervals and stores them in Supabase. Without this job, historical story performance data would be unavailable in the Best Performing Reels page.
4. **Token Health Monitoring** â€” the server monitors the validity of the Meta Access Token. If the token is expired or missing, affected pages display a permission error with instructions to regenerate the token in Facebook Graph API Explorer with the `leads_retrieval` permission. Note: User Access Tokens for Meta expire approximately every 90 days and must be renewed manually.
5. **Revenue Data Polling** â€” Google Sheets revenue figures are polled automatically every 30 seconds and surfaced in the KPI cards on the Ads Analytics Dashboard.
6. **AI Lead Saturation Check** â€” the latest Campaign Saturation analysis result is fetched from the AI API on each load of the Dashboards page and displayed as a saturation alert banner if saturated campaigns are detected.

## 1.3 Who This Manual Is For

This manual is intended for all users of the MHS Marketing Dashboard. The system supports three distinct user roles, each with a different scope of access.

### 1.3.1 Administrators

Administrators have unrestricted access to every page, feature, and setting within the dashboard. This includes all analytics modules, lead management, AI Insights, content performance, and the Team Management settings. Administrators are responsible for:

1. Adding, editing, and removing team member accounts.
2. Configuring access permissions for Restricted users.
3. Renewing the Meta Access Token when it expires.
4. Configuring server environment variables (API keys, database URLs, storage keys).

This manual is the primary reference for Administrators setting up and maintaining the system.

### 1.3.2 Managers and Marketing Team Members

Managers and day-to-day marketing users access the dashboard to monitor campaign performance, review lead data, analyse content results, and act on AI-generated recommendations. These users will primarily use:

1. The Ads Analytics Dashboard for paid campaign monitoring.
2. The Best Performing Ad and Best Performing Reels pages for creative analysis.
3. The AI Insights page for strategic recommendations and lead scoring.
4. The Audience page for demographic and geographic data.
5. The Content Marketing Dashboard for organic performance tracking.

### 1.3.3 Restricted Users

Restricted users are team members whose access has been limited to specific modules by an Administrator via the Manage Permissions page. A Restricted user may, for example, be granted access only to the Reels analytics page and not to lead data or financial metrics. Restricted users should refer to their Administrator for clarification on which modules they can access.

## 1.4 How the System Connects to External Platforms

The following table summarises how the dashboard connects to each external platform and what data flows in each direction.

### 1.4.1 Meta / Facebook and Instagram

- **Connection method:** Meta Graph API using a User Access Token stored in the server `.env` file as `META_ACCESS_TOKEN`.
- **Data retrieved:** Ad campaign spend, impressions, clicks, leads, CPL, CTR, Hook Rate, Hold Rate, ROAS, conversion metrics, organic page views, interactions, reach, follower counts, unfollow counts, audience demographics (age, gender, city, country), Instagram Reel performance (views, shares, saves, comments, watch time), and lead form submissions (name, phone number, custom fields).
- **Scope of permissions required on the Meta token:** `leads_retrieval`, `pages_read_engagement`, `read_insights`, `ads_read`.
- **Token expiry:** User Access Tokens expire approximately every 90 days. When the token expires, lead tables and analytics sections that rely on live Meta data will display a permission error. The token must be regenerated in Facebook Graph API Explorer and updated in the server environment by an Administrator.

### 1.4.2 Wix Website

- **Connection method:** Wix Analytics REST API using a Wix API Token (`WIX_TOKEN`) and Site ID (`WIX_SITE_ID`) stored in the server `.env` file.
- **Data retrieved:** Total site sessions, unique visitors, clicks to contact, form views, form submissions, and lead count. Session data is also broken down by traffic source.
- **Limitation:** Wix analytics data is available for a maximum of 62 days. Requests for date ranges exceeding 62 days will return an error.

### 1.4.3 Google Sheets

- **Connection method:** Google Sheets API using service account credentials configured on the backend server.
- **Data retrieved:** Online Conversion values, Offline Conversion values, L1 Revenue, L2 Revenue, Total Revenue, Organic Revenue (filtered by date range and source). The Paid Leads sheet is also used for phone-matched conversion counting on the Best Performing Ad page.
- **Polling frequency:** Revenue KPI cards are refreshed every 30 seconds automatically.

### 1.4.4 YouTube / Google Ads

- **Connection method:** Google Ads API or YouTube Data API, configured via credentials on the backend server.
- **Data retrieved:** YouTube advertising cost, conversions, CPL, CPM, Opt-in Rate, Link Clicks, CTR, and ROAS. Available when the Platform filter in the Ads Analytics Dashboard is set to YouTube.

### 1.4.5 Google Gemini AI

- **Connection method:** Google Gemini API key stored in the server environment, accessed via the backend `/api/ai/` routes.
- **Data sent:** Structured Meta Ads performance data, Instagram Reel metrics, and lead data are sent to Gemini for analysis.
- **Data received:** Lead Saturation Index and signal scores, Creative Fatigue scores, Lead Quality scores and tier classifications, strategic action recommendations, and natural-language AI responses.
- **Note:** Gemini API quota limits apply. If the quota is exceeded, the AI Insights page displays a countdown timer before allowing a retry.

## 1.5 System Requirements

To use the MHS Marketing Dashboard, the following requirements must be met.

### 1.5.1 For End Users (all roles)

1. **Web browser:** A modern, up-to-date web browser is required. Supported browsers include Google Chrome (recommended), Mozilla Firefox, Microsoft Edge, and Safari. The dashboard uses responsive design and functions on both desktop and mobile screen sizes, though desktop use is recommended for data tables and chart analysis.
2. **Internet connection:** A stable internet connection is required. The dashboard loads live data from Meta, Google Sheets, Wix, and other external APIs on demand. Slow or intermittent connections may cause data loading delays or timeout errors on pages with large API responses (such as the AI Insights page, which has a 120-second timeout for Gemini analysis).
3. **Credentials:** A valid dashboard account (email address and password) is required. Accounts are created by an Administrator via the Team Management page (Settings > Team Management), or via the Signup page at `/signup`. Users who have forgotten their password must contact their Administrator, as there is no self-service password reset feature in the current system.

### 1.5.2 For Administrators (server configuration)

1. **Node.js server** running with all required environment variables configured in `server/.env`: `META_ACCESS_TOKEN`, `META_AD_ACCOUNT_ID`, `REACT_APP_API_BASE`, `REACT_APP_STORAGE_KEY`, `WIX_SITE_ID`, `WIX_TOKEN`, Google Sheets API credentials, and the Gemini API key.
2. **PostgreSQL database** accessible from the server with the correct connection string.
3. **Supabase project** configured for Instagram Stories snapshot storage.
4. The React frontend application built and deployed with the correct `REACT_APP_API_BASE` environment variable pointing to the live backend URL.

## 2.1 Accessing the Dashboard

### URL

The MHS Marketing Dashboard is a web-based application. To access it, open your browser and navigate to the URL provided by your system administrator. The login page is served at the `/login` route of that base URL (for example: `https://yourdomain.com/login`).

If you attempt to navigate directly to any dashboard page (such as `/leads` or `/analytics`) without being logged in, the application will automatically redirect you to the Login page. After you log in successfully, you will be sent to the page you originally tried to reach.

### Browser Requirements

The dashboard is designed to run in any modern, standards-compliant web browser. The following are recommended for the best experience:

- Google Chrome (version 90 or later)
- Mozilla Firefox (version 88 or later)
- Microsoft Edge (version 90 or later)
- Safari (version 14 or later, macOS and iOS)

**Requirements:**

- JavaScript must be enabled in your browser. The application is a React single-page application and will not function without JavaScript.
- Cookies and `localStorage` (browser local storage) must be enabled. The application stores your authentication token in `localStorage`. If your browser is set to block local storage (for example, in strict private/incognito mode with enhanced tracking protection), the login session will not persist after the page is closed or refreshed.
- A stable internet connection is required to communicate with the backend API server.

**Not supported:**

- Internet Explorer (any version) is not supported.
- Browser extensions that aggressively block JavaScript or storage (such as certain script-blockers or privacy tools) may interfere with the authentication flow. If you experience unexpected login issues, try disabling such extensions temporarily.

## 2.2 Login Process

### Overview

The Login page is identified by the heading **"Welcome Back!"** and the subtext **"Sign in to your account."** It contains an email field, a password field with a visibility toggle, and a **Login** button.

### Step-by-Step Login Instructions

**Step 1 â€” Open the Login page.**

Navigate to the dashboard URL in your browser. If you are not already authenticated, you will land on (or be redirected to) the Login page at `/login`.

**Step 2 â€” Enter your email address.**

Click the **Email** input field (labelled with an envelope icon and placeholder text "Enter your email"). Type the email address that is registered with your dashboard account. The browser's autocomplete feature is enabled for this field, so saved email addresses may be suggested.

**Step 3 â€” Enter your password.**

Click the **Password** input field (labelled with a padlock icon and placeholder text "Enter your password"). Type your account password. The characters you type are masked by default.

- To reveal the characters you have typed, click the **"Show"** toggle button on the right side of the password field.
- To re-mask the characters, click the same toggle again (it will display **"Hidden"** when the password is masked).

**Step 4 â€” Click the Login button.**

Click the **Login** button to submit your credentials. While the application is communicating with the server:

- The button text will change to **"Signing in..."**
- Both input fields and the button will be disabled to prevent duplicate submissions. Do not click the button more than once.

**Step 5 â€” Review the outcome.**

- **On success:** You will be automatically redirected to the dashboard home page, or to the specific dashboard page you originally tried to access before being redirected to login. No further action is needed.

- **On failure:** A red error alert banner will appear above or within the form, displaying a message that describes what went wrong. See Section 2.7 for a full list of error messages and how to resolve them.

### Important Notes on the Login Form

- Both the Email and Password fields must be filled in before the form can be submitted. If either field is empty when you click Login, the error **"Please fill in all fields"** will appear immediately, without contacting the server.
- The form is fully accessible: the form container carries an `aria-label` of "Login form" and the error banner uses `role="alert"`, which means screen readers will announce errors automatically.

## 2.3 Session Management

### How Sessions Work

The MHS Marketing Dashboard uses **JSON Web Tokens (JWT)** for authentication. When you log in successfully, the server issues a JWT token along with your user profile object. These are stored in your browser's `localStorage` under two keys:

- `ads_dashboard_auth` â€” the primary key used by the application's authentication context (stores both the token and user object as JSON).
- A secondary key defined by the `REACT_APP_STORAGE_KEY` environment variable (defaults to `app_auth`) â€” used by a companion authentication utility.

Because the token is stored in `localStorage`, **your session persists across page refreshes and browser restarts**. You do not need to log in again simply because you closed and reopened the browser tab, as long as the token is still valid on the server.

### Automatic Session Restore

When you return to the dashboard (for example, after a browser restart or a new tab), the application automatically reads the stored token from `localStorage`. If a token is found:

1. The application treats you as logged in immediately and loads the dashboard.
2. If the token is present but the user profile object is missing or incomplete, the application silently contacts the server at `/api/auth/me` to verify the token and retrieve the current user profile.
3. If the server confirms the token is valid, the user profile is restored and the session continues normally.
4. If the server rejects the token (because it has expired or been revoked), the application automatically clears the stored session and redirects you to the Login page.

### What Happens When Your Session Expires

There is no client-side session timer. The token remains active in `localStorage` until one of the following occurs:

- **Server-side rejection:** On the next app load, when the application calls `/api/auth/me` to validate the token, the server rejects it. The application then logs you out automatically and redirects to `/login`.
- **Manual logout:** You explicitly log out (see Section 2.6), which immediately clears the token and ends the session.
- **Browser storage cleared:** If you clear your browser's site data, cookies, or `localStorage` (for example, through browser settings or developer tools), the token is deleted and you will need to log in again the next time you visit the dashboard.

### Protected Routes

Every page of the dashboard â€” except `/login` and `/signup` â€” is protected. This means:

- If the application does not find a valid session in `localStorage` when you navigate to a protected page, you are immediately redirected to `/login`.
- After you log in, the application remembers the page you originally tried to access and redirects you there automatically.

## 2.4 Signup / Account Creation

### Overview

New users who do not yet have a dashboard account can create one from the **Signup page** at `/signup`. You can reach this page by:

- Navigating directly to `/signup` in your browser.
- Clicking the **"Sign Up"** link at the bottom of the Login page (below the "Don't have an account?" text).

On successful registration, the account is created, you are automatically logged in, and you are redirected to the dashboard home page â€” no separate login step is required.

### Step-by-Step Account Creation

**Step 1 â€” Open the Signup page.**

Navigate to `/signup` or click the **Sign Up** link on the Login page.

**Step 2 â€” Enter your full name (optional).**

The **Full Name** field is labelled with placeholder text "(optional)". You may enter your full name here or leave it blank. Leaving it empty will not prevent the form from being submitted.

**Step 3 â€” Enter your email address (required).**

Click the **Email** field and type a valid email address. This address will become your login identifier. The browser's native format validation applies, so an address without an "@" symbol and a domain (for example, "user@example.com") will be rejected before the form is submitted.

**Step 4 â€” Create a password (required).**

Click the **Password** field (placeholder: "Create a password") and type the password you want to use for this account. The field is masked for security. Password strength and minimum length requirements, if any, are enforced by the backend server; any such rule violations will be shown in the error banner.

**Step 5 â€” Confirm your password (required).**

Click the **Confirm Password** field (placeholder: "Confirm password") and re-type the exact same password you entered in Step 4.

- If the two password fields do not match, the error **"Passwords do not match"** will appear immediately when you attempt to submit, without contacting the server.
- Correct the mismatch and try again.

**Step 6 â€” Submit the form.**

Click the **Sign Up** button. While the request is being processed:

- The button text changes to **"Creating..."**
- All four input fields and the button are disabled to prevent duplicate submissions. Do not click the button more than once.

**Step 7 â€” Review the outcome.**

- **On success:** The account is created, your JWT token is stored in `localStorage`, you are logged in automatically, and you are redirected to the main dashboard home page (`/`).

- **On failure:** An error alert banner appears at the top of the form with a message describing the problem (for example, "Email already in use", a password policy violation, or a network error). Correct the indicated issue and click **Sign Up** again.

### Notes on Account Creation

- Email, Password, and Confirm Password are all required fields. Full Name is optional.
- If the error banner shows a message about the API server URL not being configured, this is an administrator-level configuration issue. Contact your system administrator and refer them to the `REACT_APP_API_BASE` environment variable setting.
- There is no email verification step visible in the current implementation. Once the server accepts the signup request, the account is active immediately.

## 2.5 Password & Security

### Password Visibility Toggle

On the Login page, the password field includes a **password visibility toggle** button on the right side of the field. Click it to switch between:

- **"Hidden"** â€” the password characters are masked (default).
- **"Show"** â€” the password characters are displayed in plain text.

Use this toggle carefully, especially in shared or public spaces where others may be able to see your screen.

### Password Complexity

Password complexity and minimum length rules are enforced by the backend server. The current client-side interface does not display specific password requirements before you attempt to create an account. If the server rejects a password during signup, the reason will be shown in the error banner. Contact your system administrator for specific password policy details.

### Forgot Password / Password Reset

There is **no "Forgot Password" or self-service password reset feature** in the current version of the dashboard. If you forget your password, you must contact your system administrator to have your password reset manually on the server.

### Session Security Considerations

- Your authentication token is stored in plain `localStorage` in the browser. This means:
  - Shared computers: If you use the dashboard on a shared or public computer, always log out explicitly when you are done (see Section 2.6) and do not allow the browser to save your password.
  - Clearing storage: Clearing your browser's site data or `localStorage` (through browser settings or developer tools) will end your session. You will need to log in again.
  - The token does not have a client-enforced expiry. Its validity is determined entirely by the server. If your organisation's security policy requires forced re-authentication after a period of inactivity, this must be configured at the server level.

### Role-Based Access

The Login and Signup pages themselves do not enforce role-based access control. All authenticated users gain access to the same set of dashboard pages. If your organisation uses different access levels (for example, administrator versus read-only user), these distinctions are determined by the server when your account was created and are reflected in the user profile returned after login.

## 2.6 Logout Process

### How to Log Out

To log out of the MHS Marketing Dashboard, click the **Logout** button or menu item available within the dashboard navigation. The exact location of the Logout control depends on the dashboard layout (typically in the top navigation bar or a user/profile menu).

When you click Logout:

1. The application immediately calls the internal `logout()` function.
2. Your JWT token and user profile are removed from both the application's memory (React state) and `localStorage` (`ads_dashboard_auth` key and the secondary `app_auth` key).
3. The session is terminated instantly â€” there is no confirmation prompt.
4. On your next attempt to navigate to any dashboard page, the ProtectedRoute guard will detect that no valid token is present and redirect you to the Login page (`/login`).

### Best Practices for Logging Out

- Always log out explicitly when using a shared or public computer.
- After logging out, you can confirm the session has ended by checking that the browser redirects to `/login` and that the dashboard pages are no longer accessible without entering credentials again.
- Closing the browser tab without logging out does **not** terminate your session. The token will still be present in `localStorage` and will restore your session the next time you visit the dashboard URL in the same browser.

## 2.7 Common Login Issues and Solutions

### Issue 1: "Please fill in all fields"

**Symptom:** The red error banner appears immediately after clicking Login, without the button entering the "Signing in..." state.

**Cause:** One or both of the Email and Password fields are empty.

**Solution:** Ensure that both the Email field and the Password field contain text, then click Login again.

---

### Issue 2: "Invalid credentials" (or similar authentication error)

**Symptom:** The error banner appears after the "Signing in..." loading state completes, with a message such as "Invalid credentials" or "Incorrect email or password."

**Cause:** The email address or password you entered does not match any account on the server, or the password is incorrect.

**Solution:**
1. Double-check that you are using the correct email address for your account.
2. Use the password visibility toggle ("Show") to confirm you are typing the password correctly.
3. Check that Caps Lock is not enabled on your keyboard.
4. If you have forgotten your password, contact your system administrator â€” there is no self-service password reset in the current version.

---

### Issue 3: Network error / server unreachable

**Symptom:** The error banner shows a network-related message (for example, "Network error", "Failed to fetch", or similar) after clicking Login.

**Cause:** The application cannot reach the backend API server. This can be caused by:
- The backend server is not running.
- The `REACT_APP_API_BASE` environment variable is not configured correctly in the deployment.
- A network or firewall issue is blocking the connection between the browser and the server.

**Solution (end user):**
1. Check your internet connection.
2. Try refreshing the page and attempting to log in again.
3. If the error persists, contact your system administrator. Inform them of the error message shown.

**Solution (administrator):**
1. Verify that the backend server process is running and accessible.
2. Confirm that the `REACT_APP_API_BASE` environment variable is set to the correct live backend URL and that the frontend application has been rebuilt and redeployed with this value.
3. Check that any firewall, proxy, or CORS settings allow the browser to reach the API endpoint at `POST /api/auth/login`.

---

### Issue 4: "Login failed: no token received"

**Symptom:** The error banner displays "Login failed: no token received" even though the server did not return an error status.

**Cause:** The backend API returned an HTTP 200 (success) response, but the JSON response body did not include a `token` field.

**Solution:** This is a backend configuration or code issue. Contact your system administrator. The server's `/api/auth/login` endpoint must return a JSON body containing a `token` field on successful authentication.

---

### Issue 5: Redirected back to Login immediately after appearing to log in

**Symptom:** The login appears to succeed momentarily, but you are immediately redirected back to `/login` instead of reaching the dashboard.

**Cause:** The session was not persisted correctly in `localStorage`. This typically occurs when:
- The browser is blocking `localStorage` (for example, in certain private/incognito modes with strict privacy settings, or when third-party storage is blocked).
- A browser extension is preventing storage access.

**Solution:**
1. Check your browser's privacy or storage settings. Ensure that `localStorage` is not blocked for the dashboard's domain.
2. Try disabling browser extensions (particularly ad blockers, script blockers, or privacy tools) and attempt to log in again.
3. Try using a standard (non-private/incognito) browser window.
4. If the issue persists, try a different supported browser.

---

### Issue 6: Session unexpectedly expired / returned to Login after a browser restart

**Symptom:** You previously logged in and the session was working, but after restarting your browser or opening the dashboard in a new tab you are sent to the Login page again.

**Cause:** One of the following:
1. Your JWT token has expired and the server rejected it when the application tried to validate it at startup.
2. Your browser's `localStorage` was cleared (either manually, by a browser setting, or by a privacy-clearing tool).
3. You used a private/incognito browser window where storage does not persist after the window is closed.

**Solution:**
1. Log in again with your credentials.
2. If this recurs frequently, check whether your browser is configured to clear site data on exit. Disable that setting for the dashboard's domain if you need persistent sessions.
3. Contact your system administrator if you believe the token expiry period is too short.

---

### Issue 7: Login page heading says "Welcome Back!" but this is my first time

**Note:** The heading "Welcome Back!" appears on both the Login page and the Signup page. This is a known cosmetic issue in the current version of the application and does not affect functionality. You are on the correct page as long as the URL shows `/login` (for existing users) or `/signup` (for new account creation).

---

### Issue 8: Passwords do not match (during Signup)

**Symptom:** On the Signup page, after clicking "Sign Up", the error "Passwords do not match" appears.

**Cause:** The text entered in the Password field and the Confirm Password field are not identical.

**Solution:**

### 3.4.3 How Theme Application Works

Components that need to respond to theme changes programmatically listen for the custom `themechange` window event, which is fired every time a theme is applied. If the System theme is selected and the OS preference changes (e.g. the device enters or exits dark mode automatically at sunset), the dashboard updates reactively without any user action.

## 4.1 Meta Ads Overview â€” Metrics Shown

The Ads Analytics Dashboard is the central reporting surface for all paid advertising activity running through Meta (Facebook and Instagram). When you open the Dashboards page at /dashboards, the system immediately loads the last 7 days of data across all configured ad accounts and presents the results across two rows of KPI (Key Performance Indicator) cards.

### Row 1 â€” Primary Performance Cards

**Ad Spend**
The total amount of money spent on Meta ads in the selected date range, denominated in Indian Rupees (INR). This is the gross spend figure as reported by the Meta Ads API before any adjustments.

**Total Leads**
The total number of lead form submissions collected via Meta Instant Forms across all selected ad accounts, campaigns, and ads in the period.

**CPL â€” Cost Per Lead**
The average cost to acquire one lead. Calculated as: Ad Spend divided by Total Leads. A lower CPL indicates more efficient lead generation. For example, if you spent â‚¹10,000 and collected 50 leads, CPL = â‚¹200.

**CTR â€” Click-Through Rate**
The percentage of people who saw the ad (impressions) and then clicked on it. Calculated as: (Clicks / Impressions) x 100. A higher CTR indicates that the ad creative and copy are resonating with the audience. Industry benchmarks for Meta typically sit between 0.5% and 2%; rates above 2% are considered strong.

**Hook Rate**
The percentage of people who paused on the video ad long enough to watch at least 3 seconds. Calculated as: (3-Second Video Views / Impressions) x 100. Hook Rate measures how effectively the first few seconds of a video capture attention before a viewer scrolls past. Higher is better. When Meta does not return 3-second view data, the system falls back to total video plays divided by impressions.

**Hold Rate**
The percentage of viewers who reached the 50% midpoint of a video ad, expressed relative to 3-second views. Calculated using the p50 (50th percentile) watch-time metric from Meta, divided by 3-second views. Hold Rate measures how well the ad retains viewer attention after the initial hook. Fallback calculations use p75, ThruPlays, p100, plays, or impressions if the primary data is unavailable. Hook Rate and Hold Rate are only meaningful for video creatives; non-video ads show a dash.

**ROAS â€” Return on Ad Spend**
The revenue generated for every rupee spent on advertising. Calculated as: Total Revenue / Ad Spend. A ROAS of 3 means â‚¹3 in revenue was generated for every â‚¹1 spent. ROAS is the single most important indicator of whether a campaign is profitable. Revenue figures used in this calculation are sourced from Google Sheets (see Row 2 cards below).

### Row 2 â€” Volume and Conversion Cards

**Impressions**
The total number of times any ad was displayed to any user, including repeat views by the same person. Impressions measure raw exposure volume.

**Clicks**
The total number of clicks on ads, including clicks on links, call-to-action buttons, and the ad image or video. This is the total-clicks figure, not unique clicks.

**Conversions**
The number of defined conversion events recorded by Meta's pixel or Conversions API for the selected period.

**Conversion Rate**
The percentage of leads that converted into a paid enrolment or purchase. Calculated as: (Conversions / Total Leads) x 100.

### Revenue Cards (sourced from Google Sheets, polled every 30 seconds)

**Online Conversion**
Revenue from conversions completed through online payment channels.

**Offline Conversion**
Revenue from conversions completed through offline channels (direct bank transfer, in-person payment, etc.).

**L1 Revenue**
Revenue attributed to Level 1 (L1) course or product enrolments.

**L2 Revenue**
Revenue attributed to Level 2 (L2) course or product enrolments.

**Total Revenue**
The sum of all revenue streams (Online + Offline, L1 + L2) for the selected period. This figure drives the ROAS calculation.

### Note on CPM and CPC

**CPM â€” Cost Per Mille (Cost Per 1,000 Impressions)**
CPM is displayed prominently in the Best Performing Ad module (Section 4.4) and in the Best Performing Reels module (Section 4.5). It measures how much you pay for every 1,000 times an ad is shown. Calculated as: (Ad Spend / Impressions) x 1,000. Lower CPM means you are reaching audiences more cost-effectively. CPM is influenced by audience competitiveness, placement, seasonality, and ad quality score.

**CPC â€” Cost Per Click**
CPC does not appear as a dedicated KPI card in the main dashboard but is derivable from the table data. Calculated as: Ad Spend / Total Clicks. CPC measures efficiency of paid traffic acquisition. A lower CPC with a high CTR indicates a well-targeted, high-quality ad.

## 4.8 Data Refresh Schedule

### Automatic Background Refresh

**Lead Tables â€” every 15 minutes**
The server runs a background sync job that fetches new leads from all accessible Meta pages every 15 minutes and writes them to the local database. The lead tables on the dashboard read from this local database, so the data displayed can be up to 15 minutes behind real-time.

**Revenue KPI Cards â€” every 30 seconds**
The Online Conversion, Offline Conversion, L1 Revenue, L2 Revenue, and Total Revenue cards poll Google Sheets every 30 seconds automatically. No user action is required.

**Campaign Saturation Alert â€” on page load**
The red saturation alert banner (if any saturated campaigns are detected) is fetched once from the AI Insights API when the Dashboards page loads. It does not auto-refresh during the session; reload the page to get a fresh saturation check.

### Manual Refresh Options

**Refresh Data button**
Reloads the Meta Ads data from the server-side cache (database). This is fast and does not count against Meta API rate limits. Use this when you want to pick up leads that have been synced in the last 15 minutes without doing a full live fetch.

**Refresh with Live Data button**
Forces a fresh fetch directly from the Meta Graph API, bypassing the local cache entirely. This is the only way to get the most up-to-date Hook Rate and Hold Rate values, since video metrics (3-second views, watch time percentiles) are updated by Meta in near-real-time. It also reloads the full ad account, campaign, and ad name lists. This button should be used sparingly to avoid hitting Meta API rate limits during peak reporting periods.

**Sync All Leads button**
Triggers an immediate on-demand server-side sync from all accessible Meta pages, independent of the 15-minute background job cycle. After the sync completes, the Ads Analytics Leads table refreshes automatically. Use this button when you know a campaign has just ended or a form has just received submissions and you need the data immediately without waiting for the next scheduled sync.

**Per-table Refresh button (Total Leads Admin View)**
Each lead table has its own Refresh button that reloads that specific table from the local database without triggering a full-page data reload.

### Best Performing Ad Module â€” Always Live

The Best Performing Ad page does not use the server-side cache. Every filter change (date range, project, ad account) triggers a live fetch directly from the Meta Ads API. There is no separate refresh button; changing a filter constitutes a fresh fetch. Conversion Count and ROAS data loads slightly after the main table data because it requires a separate server-side phone-matching process against the Paid Leads sheet.

### Best Performing Reels Module â€” Always Live

The Best Performing Reels page also fetches live from the Meta Graph API on every filter change (platform, page, date range, content tab). There is no cache layer on this page. The media insights request has a hard 45-second timeout; if the Meta API is slow or the page has a large volume of content, a timeout error may appear. The recommended action is to narrow the date range and retry.

### Meta Token Validity

All Meta API calls depend on a valid META_ACCESS_TOKEN configured in the server environment. If this token has expired, all Meta data fetches will return a permission or authentication error displayed in the dashboard. The token must be regenerated in the Facebook Graph API Explorer with the leads_retrieval permission. Refer to the system administrator for token rotation procedures.

## 5.1 Unique Leads Overview

The Unique Leads page (`/unique-leads`) is the central tool for managing lead deduplication across acquisition sources. ## 5.3 Lead Quality Scoring

The Lead Intelligence Scoring Service (`server/services/leadQualityScoringService.js`, methodology version `Lead_Intelligence_MHS_v1.0`) automatically evaluates every lead on a numeric scale from 0 to 150 and places it into one of four action tiers.

**How scores are calculated**

Each lead receives points from two independent factors that are added together to produce the total score.

**Factor 1 â€” Sugar Level (maximum 40 points)**

The lead's blood sugar level is parsed from the Sugar Poll field, which accepts free-text or numeric values. The system converts the text to an estimated mg/dL reading and assigns points as follows:

| Blood Sugar Level | Estimated mg/dL | Points |
|---|---|---|
| Very High | Above 250 mg/dL | +40 |
| High | 180 â€“ 250 mg/dL | +30 |
| Controlled | 126 â€“ 180 mg/dL | +20 |
| Borderline | Below 126 mg/dL | +10 |

The parser accepts values like "above 250", "controlled", "borderline", plain numbers such as "220", and common label strings. Unrecognisable values result in zero sugar points.

**Factor 2 â€” Behavioural Engagement (maximum 110 points)**

Behavioural signals are read from the `lead_intel` JSON field on the Leads table. These signals are populated by external CRM tools such as GHL or TagMango, or entered manually. The available signals and their point values are:

| Behaviour | Points |
|---|---|
| WhatsApp message opened within 1 hour | +15 |
| Clicked a link | +20 |
| Replied to a message | +25 |
| Visited the payment page | +30 |
| Attended a masterclass | +35 |
| Asked a question | +20 |
| Previous buyer | +50 |
| Age between 45 and 60 | +10 |

If `lead_intel` data is not populated for a lead, only the sugar level points are computed. Most leads will score low in this situation, so populating `lead_intel` is required for meaningful tier differentiation.

**Tier classification and follow-up actions**

| Tier | Score Range | Display Label | Recommended Follow-Up |
|---|---|---|---|
| Hot | 80 â€“ 150 | Hot Lead | Personal call within 2 hours |
| Warm | 50 â€“ 79 | Warm Lead | WhatsApp sequence within 24 hours |
| Nurture | 25 â€“ 49 | Nurture | Follow-up sequence within 48 hours |
| Cold | 0 â€“ 24 | Cold | Weekly broadcast only |

**Benchmark targets**

The scoring service documentation sets the following performance benchmarks: average score above 45 and hot lead rate above 25%. If the dashboard shows values below these thresholds, it is typically a signal that `lead_intel` behavioural data is not being captured or populated.

**Score persistence**

Scored results are upserted to the `lead_scores` Supabase table. Re-scoring the same date range updates existing records rather than creating duplicates. Scores are retrieved and filtered by `updated_at`, not `created_at`, so re-scored leads remain visible in the correct date window.

**Running batch scoring**

Batch scoring is triggered by calling `runLeadScoring({ dateFrom, dateTo, campaignIds })` where `dateFrom` and `dateTo` are required in `YYYY-MM-DD` format and `campaignIds` is an optional filter. ## 5.5 Lead Deduplication Logic

The Unique Leads system enforces a single canonical record per phone number across all source categories. The deduplication key is always the **last 10 digits** of the submitted phone number. Country codes, leading zeros, and any other prefix characters are stripped automatically. Phone numbers with fewer than 10 digits after stripping are rejected entirely and counted in the "rows skipped" total shown in the import summary.

**Scientific notation handling**

Phone numbers stored in Excel files as scientific notation (for example, `9.18E+09`) are automatically expanded to their full numeric form before the last-10-digit extraction is applied.

**Within-file deduplication**

Before any database insertion, the system deduplicates within the uploaded file itself. If the same phone number appears more than once in a single upload, it is counted only once.

**Cross-source priority resolution**

When an imported phone number already exists in the `unique_leads` table, the system compares the priority rank of the incoming source against the stored record:

- **Incoming source has higher priority than stored record** (example: uploading a Paid file when the number is stored under YouTube): The stored record's `lead_source_type` is updated to the new higher-priority label. This is counted as an "upgrade" in the import summary. No duplicate entry is created.

- **Incoming source has lower priority than stored record** (example: uploading a YouTube file when the number is already stored as Paid): The incoming record is NOT inserted into `unique_leads`. Instead, it is written to the `duplicate_leads` table for review. The canonical record is unchanged.

- **Incoming source matches stored record's priority** (same source uploaded again): The record is silently skipped. No error is raised and no duplicate entry is created.

- **Paid source is always the highest priority**: Uploading a Paid file upserts all records unconditionally, overriding any lower-priority source already stored for those phone numbers.

**Post-import duplicate modal**

If any duplicates are detected during an import, a modal dialog appears automatically after the import completes. The modal displays the count of conflicts found and offers two options: "Download Duplicate File" (saves a CSV of the flagged records) or "Skip and Continue" (dismisses the modal without downloading).

**Auto-deletion policy**

All imported leads are subject to automatic server-side deletion after 30 days. The system calculates the countdown from the `created_at` timestamp of the oldest record in the filtered category. A countdown banner appears at the top of each category view:

- Normal (more than 7 days remaining): standard banner showing days remaining and expiry date
- Warning (7 days or fewer remaining): yellow banner
- Urgent (0 days remaining): red banner

The table's meta row uses the authoritative total from the auto-delete-info endpoint to display the true record count, even when the table display is capped at 1,000 rows.

## 5.6 Auto-Sync from Meta (Background Lead Sync Jobs)

Two separate background jobs run on the server to pull Meta lead form submissions into the dashboard database automatically. These jobs require no user action once the server is configured.

**15-minute database sync job (`server/jobs/leadsSync.js`)**

This job runs immediately on server startup and then repeats every 15 minutes. It:

1. Reads the last successful sync timestamp from the `lastSuccessfulLeadsSyncUtc` key in the database job state store.
2. Subtracts a 10-minute overlap window from that timestamp to catch any late-arriving leads.
3. Discovers all lead generation forms associated with each Facebook Page listed in the `META_PAGE_IDS` environment variable.
4. Fetches leads from Meta's Graph API (v24.0) for each form within the computed date window, paginating through up to 50 pages per form per cycle (maximum approximately 100,000 leads per form per run).
5. Parses each lead's field data into structured fields: name, phone/mobile, street/address, city, post code, sugar poll.
6. Saves new leads to the local database and advances the sync cursor.
7. On first run (or after a gap larger than 7 days), automatically performs a backfill covering up to 7 days of history.

The job uses a dual-token strategy: a Page Access Token for form discovery and a User Access Token for lead fetching, to ensure that `ad_id` and `campaign_id` attribution fields are returned. If a stored token has expired, the job automatically exchanges a fresh token rather than failing.

Meta rate-limit responses (error codes 4, 17, 32, 613) trigger automatic retry with exponential back-off, up to 5 attempts. If one Facebook Page fails, the job logs the error and continues processing the remaining pages; the sync cursor is only advanced when all pages succeed.

There is no dashboard button or API endpoint to manually trigger this job. It runs exclusively on its 15-minute server-side schedule.

**5-minute Google Sheets sync for Direct Walk-In forms (`server/routes/leadsSync.js`)**

This separate job runs every 5 minutes as a safety net and monitors only the three Direct Walk-In forms listed in Section 5.2. It:

1. Fetches new leads from Meta for each of the three forms created after the stored checkpoint in `server/data/leads-sync-state.json`.
2. Deduplicates against existing Lead IDs already present in Google Sheets column C.
3. Sorts all new leads globally by `created_time` (oldest first).
4. Appends rows in batches of 500 to the "DW-live data" tab of the configured Google Sheet.
5. Updates the per-form checkpoint (`lastSyncTime`, `lastRun`, `totalPushed`) in the state file.

Real-time delivery is also available via Meta webhook (see Section 5.9). The 5-minute poll is a fallback in case a webhook event is missed.

**Required server environment variables**

| Variable | Purpose |
|---|---|
| `META_PAGE_IDS` | Comma-separated Facebook Page IDs for the 15-minute sync job |
| `META_SYSTEM_ACCESS_TOKEN` or `META_ACCESS_TOKEN` | Meta API access token for both sync jobs |
| `META_WEBHOOK_VERIFY_TOKEN` | Webhook verification secret (default: `mhs_dw_sync_2025`) |
| `LEADS_SHEET_SYNC_MS` | Override for the 5-minute DW sync interval (minimum 60,000 ms) |

**Real-time delivery via Meta webhook**

**5-minute safety-net poll**

In case a webhook event is missed, the server also polls Meta every 5 minutes for each of the three forms. It fetches only leads created after the stored checkpoint timestamp, deduplicates against existing Lead IDs, sorts chronologically, and appends any new rows in batches of 500.

If the sheet is empty or after a prolonged outage, a full backfill can be triggered by sending a POST request to `/api/leads-sync/backfill`. This fetches up to 20,000 leads per form (200 pages of 100 leads), skips any Lead IDs already present in the sheet, sorts all results by creation time, and appends them. During a backfill, rows are written in chunks of 500 to stay within Google Sheets API limits.

**Manual incremental sync**

To force an immediate catch-up without waiting for the 5-minute poll, send a POST request to `/api/leads-sync/sync`. This runs the same logic as the scheduled poll but on demand.

**Sync status check**

Send a GET request to `/api/leads-sync/status` to inspect the current sync state. The response includes per-form `lastSyncTime`, `lastRun`, and `totalPushed` values, as well as the configured sheet ID, sheet tab name, and sync interval in minutes.

**Duplicate prevention**

Lead IDs are stored in column C of the sheet. Before any append operation, the system performs a live re-read of column C under an exclusive cross-process writer lock to confirm the Lead ID is not already present. This prevents duplicate rows even when the server is restarted or when multiple server processes run simultaneously (for example, when nodemon and a production node process run side by side).

Lead IDs are written with a leading apostrophe character to force Google Sheets to treat them as text, preventing large integer IDs from being displayed in scientific notation.

**Sync state checkpoint file**

The file `server/data/leads-sync-state.json` records the last successful sync timestamp and total rows pushed for each of the three forms. If this file is deleted or corrupted, the next incremental sync will treat all leads as new from the beginning. The deduplication logic will prevent actual duplicate rows from being inserted, but the full fetch will be slower than a normal incremental run.

**Conversion count cross-reference**

A separate service (`server/services/paidLeadsService.js`) reads a different Google Sheet â€” the "Paid leads - L1" tab in sheet ID `17pctKsTlWq93poCMVwnMzL7cPYuIfGN7coFieop2xdM` â€” to power the Conversion Count metric on the Best Performing Ad page. This sheet lists customers who actually paid. The service normalises both the primary Phone Number (column D) and the Alternate number (column E) to their last 10 digits and caches the resulting set in memory for 10 minutes. To see a newly added paid customer reflected in conversion counts immediately, use the POST `/api/conversions/refresh-paid` endpoint or append `&refresh=1` to any conversion count request.

## 6.6 Reach and Impressions Analytics

### Page Performance Area Chart

The Page Performance chart is a time-series area chart that appears in the Demographics tab when you have selected Facebook or Instagram in the Platform filter and have chosen a specific page. It shows three metrics plotted daily across your selected date range:

- **Reach** (blue area) â€” the number of unique accounts that saw any content from your page on each day. Reach counts each person only once per day, regardless of how many times they encountered your content.

- **Clicks** (teal area) â€” the number of times people clicked on any content associated with your page on each day. This includes link clicks, photo opens, video plays, and reactions that required a click action.

- **Impressions** (green area) â€” the total number of times your content was displayed on each day. Unlike Reach, Impressions count every display, including when the same person sees the same post multiple times. Impressions will always be equal to or greater than Reach.

**Plain language explanation of the key difference between Reach and Impressions:**

Suppose your page publishes one post and it is seen by 500 people. Of those 500 people, 200 see it once, 200 see it twice (perhaps they scrolled past it, left, and came back), and 100 see it three times. In this scenario:
- **Reach = 500** (500 unique people saw it)
- **Impressions = 200 + 400 + 300 = 900** (total number of displays)

A large gap between Impressions and Reach on any given day indicates that your content is being shown repeatedly to the same people â€” this can be a sign of effective retargeting or it can indicate that your content is not spreading to new audiences.

**How to read the area chart:** Each metric is filled with a semi-transparent colour beneath the plotted line, making it easy to see relative volumes at a glance. Hovering over any point on the chart shows the exact values for Reach, Clicks, and Impressions on that specific date. Look for spikes â€” a sudden increase in Reach on a particular day often corresponds to a post that performed well organically or a campaign that began serving.

## 8.1 AI Insights Overview

The AI Insights page is the marketing intelligence centre of the MHS Marketing Dashboard. It brings together data from every part of your marketing funnel â€” Meta Ads campaigns, Instagram Reels, and incoming leads â€” and uses Google Gemini AI to analyse all of it and tell you what is working, what is not, and what to do next.

Think of it as having a senior marketing analyst on call at all times. Rather than manually comparing spreadsheets and campaign reports, you open this page and receive a complete picture of your marketing health in plain language, along with specific actions to take.

The page covers four core areas of analysis:

- **Lead Saturation** â€” Is your target audience getting tired of seeing your ads?
- **Creative Fatigue** â€” Are your ad creatives losing their impact?
- **Lead Intelligence** â€” How qualified are the leads coming in, and who should be called first?
- **AI Marketing Intelligence** â€” What strategic actions should you take right now?

All four analyses run automatically when you open the page. You do not need to set anything up or press a button to get started.

## 8.2 What Insights Are Auto-Generated

When you land on the AI Insights page, the system immediately fetches your current Meta Ads and Instagram Reel data and passes it to Google Gemini. Gemini reads your real campaign names, spend figures, lead counts, cost-per-lead (CPL), reach, engagement rates, and reel performance metrics. It then generates the following automatically:

**Six Insight Cards**
Each card covers a specific topic â€” ad performance, reel performance, audience behaviour, or budget trends. Cards are colour-coded:
- Green = positive signal, things are performing well
- Amber = a warning that needs your attention
- Blue = general information to keep in mind

Each card shows the time window it covers and ends with a short action phrase telling you what to do with that information.

**Four Recommendation Cards**
These are strategic actions Gemini recommends based on your actual data. Each recommendation includes an explanation of why it is being suggested, drawn from your real campaign figures. Recommendations are colour-coded by theme â€” green for scaling opportunities, red for urgent issues, blue for audience adjustments, and purple for creative direction.

**Best Performing Ad Panel**
Identifies the single top-performing ad in your account for the selected time window. Shows the campaign name, total spend in rupees, number of leads generated, cost-per-lead, a one to two sentence explanation of why it is performing well, and a recommended action label: SCALE, MONITOR, or PAUSE.

**Best Performing Reel Panel**
Identifies the top Instagram Reel for the selected time window. Shows the reel title (extracted from the caption), reach, engagements, saves, hook rate, average watch time, engagement rate, and a thumbnail preview. The recommended action label will be REPURPOSE, BOOST, or MONITOR.

**AI Insight Feed**
A chronological list of insight cards generated from the Gemini analysis, each showing the insight type, the time window it applies to, a plain-language description, and a recommended action.

All figures in the analysis are shown in Indian Rupees (INR). Gemini is instructed to reference only your actual data and never to invent or estimate numbers.

## 8.3 How to Request or Refresh AI Analysis

**Automatic analysis on page load**
Every time you navigate to the AI Insights page, an analysis runs automatically. You will see a two-phase loading message:
1. "Loading ads and reels" â€” the system is fetching your Meta Ads and Instagram data
2. "Generating AI insights" â€” Gemini is processing the data and writing the analysis

You do not need to do anything. The four summary cards and all tables populate as each phase completes.

**Manually refreshing the analysis**
To force a completely fresh analysis at any time, click the **Refresh** button in the top-right area of the page header. This bypasses the stored data and pulls live figures directly from the Meta Ads API before re-running the Gemini analysis. Use this when you know a campaign has just been updated or a new Reel has been posted and you want the latest numbers reflected immediately.

**Changing the date range**
By default the page analyses the last 7 days. To change the period:
1. Click the date picker button in the header (it shows the current preset label and date range)
2. Select a preset: Today, Last 7 days, Last 14 days, or Last 30 days
3. For a custom window, choose Custom, enter the From and To dates, then click **Apply Range**

The entire page re-fetches and re-analyses data for the new period.

**Re-running individual analyses**
Each of the three analytical sections â€” Lead Saturation, Creative Fatigue, and Lead Intelligence Scoring â€” has its own **Re-run analysis** or **Run Scoring** button. These let you refresh one section independently without reloading the entire page. This is useful when you want updated lead scores after a batch of new leads has come in, without waiting for a full page refresh.

**Asking a specific question**
Scroll to the **Ask AI** section. You can either:
- Type any question in plain language and press Enter or click Ask AI
- Click one of the 21 pre-built query pills (covering CPL, creative direction, audience, budget, saturation, lead quality, and strategy topics) to pre-fill and submit a question instantly

The answer appears below the input, typically within a minute or two. Gemini uses your current dashboard data as context when answering, so the response will reference your actual campaigns and figures.

## 8.4 Types of Insights Provided

The AI Insights page covers four distinct categories of analysis. Here is what each one tells you in everyday terms:

**Spend Efficiency (via Best Ad Panel and Insight Cards)**
Gemini examines your ad spend relative to the leads and results produced. It identifies which campaigns are delivering a low cost-per-lead and which are burning budget without proportional results. The Best Performing Ad card tells you the single most cost-efficient ad and whether you should put more money behind it (SCALE), keep watching it (MONITOR), or cut it (PAUSE).

**Audience Insights (via Lead Saturation Analysis)**
This tells you whether you have been showing your ads to the same people too many times. When an audience has seen your ads repeatedly without converting, your costs rise and your results drop. The Lead Saturation section gives each campaign a Saturation Index score from 0 to 100 and flags campaigns in Warning or Critical state before the problem becomes severe. It also tracks what percentage of your impressions are going to people who have never seen your ad before â€” a healthy campaign should be reaching a steady stream of new eyes.

**Creative Performance Insights (via Creative Fatigue Analysis and Best Reel Panel)**
These insights track how well your ad creatives and Instagram Reels are performing over time. For ads, the system measures whether your click-through rate is declining and whether the creative is showing signs of audience boredom. For Reels, it scores each video across seven metrics and identifies which ones are trending, which should be reposted, and which are on the rise.

**Lead Quality Insights (via Lead Intelligence Scoring)**
Rather than treating all leads as equal, the Lead Intelligence section scores each incoming lead using the MHS sugar-band model. ## 8.5 Creative Fatigue Detection â€” What It Is and How to Read It

**What is creative fatigue?**
Creative fatigue happens when the same audience has seen your ad creative so many times that they stop paying attention to it. You will notice it as a falling click-through rate (CTR), rising cost-per-lead, or flat engagement even when your budget remains constant. Left unaddressed, a fatigued creative continues spending your budget while delivering fewer and fewer results.

**How the MHS Fatigue Score works**
The dashboard calculates a Fatigue Score for each ad creative using this formula:

- CTR decline accounts for 40% of the score
- Lifespan pressure (how long the creative has been running) accounts for 40%
- Hook rate decline accounts for 20%

The score runs from 0 upward. The status bands are:
- **Fresh (0â€“40)**: the creative is still performing well, no action needed
- **Aging (40â€“70)**: performance is beginning to soften, worth monitoring
- **Fatigued (70â€“100)**: performance has materially declined, plan a replacement
- **Severe (100+)**: the creative is exhausted, replace immediately

**Reading the Creative Fatigue card**
The summary card on the AI Insights page shows three figures at a glance: the average CTR drop across your creatives, the average hook and watch-time rate, and the count of creatives still in the Fresh band. Below that, the top three most fatigued creatives are listed with their status badges.

**Reading the Creative Fatigue detail table**
Scroll down to the Creative Fatigue Ads table for a full breakdown of every creative. The key columns are:

- **Frequency** â€” how many times the average person in your audience has seen this ad. High frequency combined with falling CTR is the clearest sign of fatigue.
- **Hook %** â€” the percentage of people who watched past the opening few seconds. Hover this column for the signal band label. A declining hook rate means your opening is no longer grabbing attention.
- **CTR Delta** â€” the change in click-through rate compared to the creative's earlier period. A strongly negative delta confirms audience disengagement.
- **CPL vs first 7 days** â€” how the current cost-per-lead compares to when the creative was new. A rising CPL is a direct cost indicator of fatigue.
- **Fatigue Score chip** â€” colour-coded green, amber, orange, or red according to the Fresh / Aging / Fatigued / Severe bands.
- **Weekly Audit count** â€” hover this column for a list of the specific audit flag keys (signals) that have been triggered for this creative.

Click any column header to sort the table and bring the most fatigued creatives to the top.

**What to do when a creative is fatigued**
When a creative reaches Fatigued or Severe status, the recommended response is to either retire it entirely or create a variation with a new hook, new visuals, or a reframed message. Continuing to run a Severe creative is the most common cause of an unexplained rise in CPL despite no changes to budget.

## 8.7 Insights Refresh Schedule

**How often the AI analysis updates**
The AI Insights page does not update continuously in the background. Analysis is triggered in three ways:

1. **Automatically on page load** â€” every time you open the AI Insights page, an analysis runs. If a cached result from the last 15 minutes already exists for the same date range and data, the system returns that cached result instantly rather than calling Gemini again.

2. **Manually via the Refresh button** â€” clicking Refresh always bypasses the cache and fetches fresh data from Meta Ads, then re-runs Gemini. Use this after making campaign changes or posting a new Reel.

3. **Via individual Re-run buttons** â€” each of the three analysis sections (Lead Saturation, Creative Fatigue, Lead Scoring) can be refreshed independently.

**The 15-minute cache**
To avoid exhausting the Gemini API quota, identical analysis requests within a 15-minute window return a stored result. The Last Analysed timestamp in the page header (shown as "just now", "5 min ago", "2h ago") tells you how recent the current analysis is.

If you open the page multiple times within 15 minutes with the same date range selected, you will see the same analysis result each time â€” this is by design. To force a new analysis before the 15 minutes expire, use the Refresh button.

**What restarting the server does**
The 15-minute cache is stored in server memory, not in the database. If the server is restarted, all cached results are cleared and the next page load will trigger a fresh Gemini call regardless of when the last analysis ran.

**Gemini quota limits**
If the Gemini API quota is exceeded, a banner appears on the page showing a countdown timer. The Retry button remains inactive until the timer reaches zero. This is a Google API rate limit and is typically resolved within 60 seconds. The countdown timer reflects the retry window suggested by Google. Your live Meta Ads and Reel data remains visible during this period â€” only the Gemini-generated commentary is unavailable.

## 8.8 Limitations and Best Practices

**Limitations to be aware of**

The AI analysis is only as current as the data available. Meta Ads data is read from the database cache on initial page load to prevent slow API timeouts. This means the figures shown may be a few hours behind the live Meta Ads Manager. Use the Refresh button to force a live pull when recency matters.

The Lead Intelligence Scoring table shows a maximum of 50 rows on screen. The full dataset, including all scored leads regardless of volume, is accessible only via the Download button. If you are working through a large lead batch, always download the file rather than working from the table view.

The Performance Snapshot tabs (Today, Last 7 days, Last 14 days, Last 30 days) inside the collapsible section use rolling calendar windows relative to the current date. They do not respect a custom hero date range you may have set. If you have set a custom range in the header but are looking at the Performance Snapshot, the snapshot tabs always show data ending today.

If no Reel was posted within the exact selected period, the Best Reel card will fall back to a wider window. A note will appear explaining that the displayed Reel was posted outside the selected period (for example, "No reel posted today â€” showing top reel published in the last 7 days"). This is expected behaviour, not an error.

The Ask AI feature has a two-minute timeout. If the Gemini API or the server is slow, the request will eventually time out. If this happens, verify that the backend server is running before retrying.

**Best practices for daily use**

Open the AI Insights page each morning as part of your daily marketing review. The overnight data will have accumulated and the auto-load analysis will give you an up-to-date picture to start the day.

Use the Last 7 days preset for routine monitoring. Switch to Last 14 days or Last 30 days when you need to assess trend direction or evaluate a campaign that has been running for several weeks.

After any significant budget change or creative launch, click Refresh to get an analysis that includes the update rather than relying on the cached result from before the change.

When a campaign shows a Warning or Critical saturation status, act within one to two days. Waiting for the status to become Severe will result in a measurable CPL increase that takes time to recover from once the audience has been fully exhausted.

Replace Fatigued or Severe creatives before the weekend if you are running lead campaigns, as weekend traffic tends to be higher and a fatigued creative will waste more budget in a compressed period.

Download the lead scoring file at the end of each day and share it with the team responsible for follow-up calls. Hot leads that are not contacted within two hours have a significantly lower conversion rate, and the scoring table provides the prioritised call list automatically.

If the Ask AI section is not giving specific enough answers, add context to your question. For example, instead of "Why is my CPL rising?", ask "Why is my CPL rising on the MHS Weight Management campaign in the last 7 days?" Gemini uses your dashboard snapshot as context but benefits from specificity in the question.

Do not rely on AI recommendations as a substitute for campaign manager judgement. Gemini works from the data it is given and cannot account for external factors such as seasonality, competitor activity, or offline events. Treat the recommendations as a structured starting point for your own decision-making, not as final instructions.

### 9.2.2 Campaign Conversion Report (Best Performing Ad â€” Conversion Count)

## 9.3 Setting Report Date Ranges

## 9.6 Scheduled / Automated Reports

### Operations Report

There is no scheduling capability for the Operations Report. It is a manual, on-demand view only.

### Paid Leads Cache â€” Automatic Refresh

The Conversion Count data has a built-in automatic refresh cycle for the Paid leads Google Sheet. The server caches the sheet data in memory with a 10-minute TTL. This means:

- The paid-phone set is refreshed automatically every 10 minutes without any user action.
- A customer added to the Paid leads Google Sheet will appear in conversion counts within 10 minutes of being saved.
- You can override the cache TTL by setting the environment variable `PAID_LEADS_CACHE_MS` (minimum 60,000 ms / 1 minute).

**To force an immediate refresh of the Paid leads cache** (without waiting 10 minutes):

Option 1 â€” Append `&refresh=1` to the conversion API URL:
```
GET /api/conversions/by-campaign?from=YYYY-MM-DD&to=YYYY-MM-DD&refresh=1
```

Option 2 â€” Send a POST request to the refresh endpoint:
```
POST /api/conversions/refresh-paid
```
Response: `{ "ok": true, "paidSetSize": <number>, "loadedAt": "<ISO timestamp>" }`

Both options are available to technical users or developers. Standard dashboard users do not need to perform these steps during normal use.

**Stale cache behavior:** If the Google Sheets service is temporarily unavailable during a refresh attempt, the system falls back to the previously cached paid-phone set and returns `paidStale: true` in the API response. Conversion counts remain available (based on the last successful read) rather than failing entirely.

### 9.8.2 Campaign Conversion Report Metrics

The following metrics appear in the Best Performing Ad table and are the primary output of the conversion reporting engine:

**Lead Generated from Ad (Total Leads)**
The count of all lead-gen form submissions attributed to a campaign within the selected date range, as recorded in the Supabase `leads` table. This count is based on Meta-synced lead events, not Meta's own "Leads" metric from the Ads API. Discrepancies between this count and the Meta Ads API lead count may occur due to sync timing or phone number availability.

**Conversion Count**
The number of leads from the Total Leads count whose phone number was found in the Paid leads Google Sheet. A lead is counted as converted if and only if its normalized 10-digit phone number matches either the primary phone or the alternate phone of any row in the "Paid leads - L1" sheet tab.

- Conversion Count is a lower-bound estimate. Leads with missing, blank, or malformed phone numbers are never matched, even if the customer did pay.
- A conversion is counted once per lead record. If a customer submitted the lead form multiple times, each submission is matched independently.
- Country codes (+91) and leading zeros are stripped automatically. Both `+919790845094` and `9790845094` resolve to the same 10-digit key `9790845094`.

**Conversion Rate (implicit)**
You can calculate this yourself: (Conversion Count / Total Leads) x 100. A high conversion rate indicates an ad campaign that generates leads with strong intent who follow through to purchase.

**CPL (Cost Per Lead)**
Total ad spend divided by total lead count for the campaign. Lower CPL means you are acquiring leads more efficiently. Compare CPL across campaigns to identify cost-effective lead sources.

**ROAS (Return on Ad Spend)**
Calculated as (Conversion Count x 3,999) / Amount Spend, where 3,999 is the assumed revenue per conversion in INR. This is a model-based estimate using a fixed revenue-per-conversion constant, not actual transaction revenue data from a payment gateway. Interpret ROAS as a directional indicator rather than a precise financial figure. A ROAS greater than 1x means the estimated revenue exceeds spend; a ROAS of "â€”" means no conversions were counted in that period.

**paidStale (API-level indicator)**
If the server's Paid leads cache is stale (Google Sheets was unreachable during the last refresh attempt), the API includes `paidStale: true` in its response. In the dashboard UI, conversion counts shown under these conditions are based on the last successfully loaded Paid leads data and may not reflect entries added after the last successful cache load. Use POST `/api/conversions/refresh-paid` to force a reload once Google Sheets connectivity is restored.

**paidSetSize (API-level indicator)**
The number of unique normalized phone numbers loaded from the Paid leads sheet at last refresh. A zero or unexpectedly low paidSetSize suggests the Google Sheet read failed or the sheet is empty/misconfigured.

**paidLoadedAt (API-level indicator)**
ISO timestamp of when the Paid leads cache was last successfully loaded. If this is more than 10 minutes in the past and you expect recent additions to the sheet to appear, trigger a manual refresh (see Section 9.6).

### 10.3.6 Key Security and Operational Rules

The Collaboration page contains several inline warnings that engineering and marketing teams must observe:

- **Privacy:** Only SHA-256-hashed phone numbers may be stored in Google Sheets analytics. Raw phone numbers must never be written to analytics systems.
- **QR Code:** Re-run `node generate.js` after any change to zones.config.json. Deliver QR PNG files at 1200x1200 pixels. The QR code must occupy at least 25% of the final screen creative area.
- **HTTPS / SSL:** HTTPS is mandatory for the Meta WhatsApp webhook. A valid SSL certificate is required. The WA_ACCESS_TOKEN must be rotated every 60 days, or a permanent System User token must be used.
- **Webhooks:** Validate the Tagmango webhook HMAC-SHA256 signature on every incoming request. The webhook handler must be idempotent â€” duplicate event deliveries from Tagmango must not create duplicate records.
- **Rate limiting:** Apply rate limiting to the /webhook endpoint (maximum 500 requests per minute per IP).
- **Reminder jobs:** node-schedule reminder jobs are lost on server restart. Migrate to Redis or AWS SQS for production to ensure reminder messages are never dropped.
- **CAC threshold:** If daily Customer Acquisition Cost exceeds Rs 10,000 after Month 1, escalate to the marketing team for creative and zone review.
- **WhatsApp templates:** All message template names used in reminder flows must be approved by Meta before the campaign goes live.

## 11.1 User Roles Overview

The MHS Marketing Dashboard uses a two-tier role model. Every account in the system is assigned one of two roles at the time the account is created. The role governs what the user can do inside the dashboard and which API endpoints they are permitted to call.

### Role 1: Admin

An Admin has unrestricted access to the entire dashboard. The role value stored in the database must be exactly `admin` or `Admin` (the check is case-insensitive). When an Admin logs in:

- All 14 feature-access permissions are automatically treated as ON, regardless of what is stored in the database.
- The full Settings section (Meta Settings, Team Management) is visible in the sidebar and on the Manage Permissions page.
- The Admin can add, edit, and delete any team member and can assign or revoke any permission for any user.
- The Admin is the only role that can call the `POST /api/permissions/update` endpoint.

Admins must be designated at account-creation time by another Admin. There is no self-promotion mechanism.

### Role 2: Restricted (Standard User / Team Member)

A Restricted user's access is controlled entirely by the individual permission toggles that an Admin has configured for their account. By default, when an account is first created, all 14 permissions are OFF. An Admin must explicitly grant each permission the user needs.

Restricted users:
- Can view their own permission profile in read-only mode.
- Cannot see or access the Settings section (Meta Settings, Team Management) unless an Admin has explicitly granted those permissions.
- Cannot modify any permission â€” their own or anyone else's.
- Cannot access the Team Management page unless the `team_management` permission has been granted.

Note on terminology: The application code and UI use the label "Restricted Access" for non-Admin accounts. The add-user form offers exactly two choices: "Admin Access" and "Restricted Access." There is no intermediate Manager or Executive role at the system level â€” all role-based distinctions between team members are expressed through the individual permission toggles described in Section 11.6.

## 11.5 Changing User Roles

## 11.8 Admin-Only Features

The following features are exclusively available to accounts with the `admin` role. They cannot be unlocked for Restricted accounts through permission toggles â€” they are enforced at the middleware layer on the server.

### Managing permissions for other users

Only Admins can navigate to `/manage-permissions/:userId` for a user ID other than their own. Any Restricted user who attempts to access another user's Manage Permissions URL receives an HTTP 403 response and is immediately redirected to Team Management.

### Creating, editing, and deleting team members

The API endpoints `POST /api/users`, `PUT /api/users/:id`, and `DELETE /api/users/:id` are protected by the `requireAdmin` middleware. These operations are never available to Restricted accounts, regardless of their permission configuration.

### Saving permission updates

The `POST /api/permissions/update` endpoint requires the `requireAdmin` middleware. A Restricted user cannot call this endpoint even if they attempt it directly.

### Settings section visibility

The Settings section on the Manage Permissions page (containing Access Settings, Meta Settings, and Team Management toggles) is hidden entirely in the UI for non-Admin users. Restricted users cannot see that these permission flags exist, and they cannot be granted the ability to see them.

### Admin's own permission profile

When an Admin opens their own Manage Permissions page, the system automatically sets all 14 permissions to ON and displays them in read-only mode. This is enforced client-side. It is informational â€” it reflects that Admins always have full access regardless of database state. Admins cannot reduce their own permissions through this page.

## 11.9 Security Best Practices

The following practices are recommended for all administrators of the MHS Marketing Dashboard.

### Assign the minimum necessary permissions

Every new Restricted account starts with all 14 permissions OFF. When granting permissions, give a user access only to the modules they need for their role. Avoid granting `dashboard_admin_leads`, `meta_settings`, or `team_management` to users who do not have a clear operational need for them.

### Limit the number of Admin accounts

Admin accounts bypass the permission system entirely. Create Admin accounts only for people who are responsible for user management and system configuration. Team members who only need to view or update marketing data should be created as Restricted accounts with tailored permissions.

### Treat Meta Settings access as a high-privilege permission

The `meta_settings` permission allows a user to modify the Facebook/Meta API token and page connection settings. An incorrect change here can disrupt live data feeds for the entire dashboard. Grant this permission only to the person responsible for the Meta integration.

### Treat Team Management access with care

Granting a Restricted user the `team_management` permission gives them read access to the team member list, including names, email addresses, and phone numbers. Grant this only to users who have a legitimate need to view the team roster.

### Review permissions after role changes

When changing a user from Admin to Restricted, immediately review and configure their Restricted permissions using the Manage Permissions workflow. Without explicit permission grants, the downgraded account will have no module access, which may cause operational disruption.

### Secure the JWT secret

The backend signs all session tokens using the `JWT_SECRET` environment variable. If this variable is not set, the server falls back to the insecure default value `please_change_this`. For any production deployment, a strong, randomly generated `JWT_SECRET` must be configured in the server `.env` file. Tokens are valid for 7 days; there is no automatic refresh mechanism, and there is no token revocation list â€” changing `JWT_SECRET` immediately invalidates all existing sessions.

### Communicate credentials securely

When creating a new user account, the Admin sets the initial password manually. There is no automated email invitation. Communicate the initial password through a secure channel (not plain email) and advise the new user to contact the administrator if they need a password change, as there is no self-service password reset in the current implementation.

### There is no undo for permission saves

Once the Save button is clicked on the Manage Permissions page, the changes are written to the database immediately. There is no confirmation dialog, no draft state, and no undo function. If permissions are saved incorrectly, the only remedy is to return to the Manage Permissions page, reverse the changes manually, and save again.

### Authentication tokens in browser storage

Session tokens are stored in `localStorage` under the key `ads_dashboard_auth`. Clearing browser site data or using a private/incognito window logs the user out. Administrators should be aware that tokens persist across browser restarts until the 7-day expiry or an explicit logout. Users on shared computers should always log out explicitly when finished.

## 12.1 Meta Settings Overview

The Meta API Settings page is the central control point for connecting the MHS Marketing Dashboard to Meta's advertising infrastructure. Every piece of campaign data, ad insight, lead record, and performance metric that the dashboard fetches from Facebook and Instagram flows through the credentials stored here.

### What is configurable on this page

| Field | Purpose | Required |
|---|---|---|
| App ID | Identifies your Meta application when making API calls | Yes â€” always |
| App Secret | Authenticates your application with Meta's OAuth system | Yes â€” first save only; leave blank on updates to keep existing |
| Ad Account ID | The Meta Ads Manager account to pull campaign and spend data from | Yes â€” always (format: act_XXXXXXXXX) |
| Access Token (User Token) | Authorises fetching of campaigns, ads, and insights data | Yes â€” first save only; leave blank on updates to keep existing |
| System Access Token | A separate token used exclusively for the leads retrieval API | Optional but strongly recommended |

### How credentials are stored

Credentials are saved server-side via `POST /api/meta/credentials` and loaded at page startup via `GET /api/meta/credentials`. Sensitive fields (App Secret, Access Token, System Access Token) are never returned to the browser after saving â€” when you return to this page, those fields appear blank intentionally. Only App ID and Ad Account ID are pre-filled from the saved configuration.

A green "Credentials configured!" banner with the token expiry date appears at the top of the page when credentials are already on file. The form button label changes from "Save Credentials" (first save) to "Update Credentials" (subsequent saves) to indicate the current state.

### Server dependency

The page performs a health check against `GET /api/health` with a 5-second timeout before attempting to load credentials. If the backend server on port 4000 is not running, or the connection times out, all fields remain empty and a connection error message is shown. No save operation is possible while the server is unreachable.

## 12.2 Meta API Token Management

### Token types used by the dashboard

The dashboard uses two distinct token types, each serving a different part of the API surface.

**User Access Token**
- Used for: fetching ad accounts, campaigns, ads, and insights (spend, impressions, clicks, leads, etc.)
- Set via the "Access Token (User Token)" field
- Stored in the server environment as `META_ACCESS_TOKEN`
- Expires approximately every 60â€“90 days
- Generated from the Graph API Explorer using your user account

**System Access Token**
- Used for: fetching leads from lead generation forms via the leads retrieval API
- Set via the "System Access Token" field
- Stored in the server environment as `META_SYSTEM_ACCESS_TOKEN`
- Does not expire on the same short cycle as user tokens; tied to a System User in Meta Business Manager
- Requires the `leads_retrieval` permission
- If not provided, the dashboard automatically falls back to the User Access Token for leads, which may fail when that token is a single-page-scoped token (the known "No forms found for this page" error documented in the project memory)

**Per-Page Access Token (server-side only, not configurable from the UI)**
- Used internally to exchange a System Token for a Page Access Token when calling leadgen_forms and /leads endpoints that require page-scoped authentication
- Can be set in the server `.env` file using the pattern `META_PAGE_TOKEN_<pageId>` when automatic exchange is not available (e.g., in some Vercel deployments)
- The server caches these page tokens in memory for 1 hour to reduce API call volume

### Adding a User Access Token for the first time

1. Log in to the dashboard.
2. Navigate to **Meta API Settings**.
3. Open the Graph API Explorer: [https://developers.facebook.com/tools/explorer](https://developers.facebook.com/tools/explorer)
4. In the Graph API Explorer, select your Meta App from the app selector dropdown.
5. Click "Generate Access Token". Grant the permissions listed in section 12.8.
6. Copy the generated token.
7. Return to Meta API Settings and paste the token into the "Access Token (User Token)" field.
8. Fill in all other required fields (App ID, App Secret, Ad Account ID).
9. Click "Save Credentials".
10. A green success banner confirms the save. The token expiry date appears in the credentials status banner.

### Updating an existing User Access Token

When the user token expires, only the token field needs to change â€” the App ID and Ad Account ID remain the same.

1. Navigate to **Meta API Settings**.
2. The App ID and Ad Account ID fields are pre-filled.
3. Leave App Secret blank (no change needed).
4. Paste the new token into the "Access Token (User Token)" field only.
5. Leave System Access Token blank if it does not need changing.
6. Click "Update Credentials".

Do not leave all sensitive fields blank when updating â€” the server requires at least the User Access Token when no token is already saved. If credentials are already configured, a blank Access Token field means "keep the existing token".

## 12.3 Connected Facebook Ad Accounts

### How ad accounts are connected

The dashboard does not connect to Facebook ad accounts through OAuth or a direct account linking flow. Instead, the Ad Account ID entered on the Meta Settings page determines which account's data is fetched. The server uses this ID as the default account for all campaign, ad, and insights queries.

The Ad Account ID must be entered in the format `act_XXXXXXXXX` â€” the `act_` prefix is required. The field placeholder ("act_123456789") demonstrates this format. The server strips the prefix internally when constructing Graph API URLs.

### Locating your Ad Account ID

1. Open [Meta Ads Manager](https://adsmanager.facebook.com).
2. Click the account selector in the top navigation.
3. Click on the account name you want to use.
4. Navigate to **Account Settings** (gear icon in the left sidebar).
5. The Account ID is shown at the top of the Account Settings page. Prepend `act_` to this number when entering it in the dashboard.

### Multiple ad accounts

The dashboard is built to support multiple ad accounts simultaneously. When users select filters by Project or Ad Account in the main dashboard pages, the backend fetches data across the relevant account IDs. The single Ad Account ID stored in Meta Settings serves as the default fallback only; the full list of monitored account IDs is defined separately in the server configuration and source code (`projectAdAccounts` constants). Adding a new account to monitoring requires a code-level configuration change, not just a Meta Settings update.

## 12.4 Connected Instagram Accounts

### How Instagram is connected

Instagram accounts are linked to the dashboard through the Facebook Page association, not through a direct Instagram login. The dashboard uses the Meta Graph API to:

- Resolve Instagram Business/Creator accounts linked to Facebook Pages via `resolveIgAccountsFromPages`
- Fetch Instagram audience insights (follower demographics, reach by follow type)
- Fetch Instagram media performance (views, reach, engagement per post)
- Fetch online follower activity to determine best posting times
- Capture story snapshots every 6 hours for the Top Stories by Views module

### Requirements for Instagram data to appear

1. The Instagram account must be a Business or Creator account (personal accounts do not expose the Insights API).
2. The Instagram account must be linked to a Facebook Page that is accessible via the token you have configured.
3. The User Token or System Token must include `instagram_manage_insights` and `pages_read_engagement` permissions.
4. The `META_PAGE_ID` environment variable on the server should be set to the Facebook Page ID associated with your Instagram account.

If the Instagram section of the dashboard shows no data, the most common cause is a missing `instagram_manage_insights` permission on the current token. Generate a new token with this permission and update it via Meta Settings.

## 12.5 Lead Form Connections

### How lead forms are connected

Lead forms are not configured on the Meta Settings page directly. The connection works through the Page Access Token chain:

1. The System Access Token (or User Token if no system token is configured) is used to call the Meta Graph API and retrieve a Page Access Token for each Facebook Page.
2. The Page Access Token is then used to call `/page_id/leadgen_forms` to list all forms attached to that page.
3. Leads submitted through those forms are fetched using the Page Access Token via `/{form_id}/leads`.

This means that for lead forms to work, the configured token must have access to the Facebook Page that owns the forms.

### The "No forms found for this page" recurring failure

This is the most common lead form issue. It occurs when:
- The System Access Token is not configured and the User Token is a single-page-scoped token
- The User Token was generated with `META_PAGE_ACCESS_TOKEN` (a static page token) that has expired
- The token does not have `leads_retrieval` permission

**Resolution:** Configure a System Access Token with the `leads_retrieval` permission in the System Access Token field. This permanent fix is documented in the project memory. A System User token obtained from Meta Business Manager does not carry the same single-page restriction as a user-generated token from the Graph API Explorer.

### Per-page token override

For environments where the system token cannot automatically exchange for page tokens (common on Vercel serverless deployments), individual page tokens can be hard-coded in the server `.env` file:

```
META_PAGE_TOKEN_<pageId>=<page_access_token>
```

These are cached for 1 hour in the server's in-memory store. They are not configurable from the dashboard UI and must be set by the developer directly in the environment configuration.

## 12.6 Token Expiry and Renewal Process

### Token expiry timeline

| Token type | Typical expiry |
|---|---|

3. Open the [Graph API Explorer](https://developers.facebook.com/tools/explorer).

6. Copy the new token.
7. Return to Meta API Settings.

9. Leave App Secret blank (unless it has also changed).
10. Leave System Access Token blank (unless it also needs updating).
11. Click "Update Credentials".
12. Confirm the success banner appears and the new expiry date is shown in the status banner.

### Preventing expiry disruptions

- Monitor the expiry date shown on the Meta Settings page.
- Set a calendar reminder 1 week before the token expires.
- Consider configuring a System Access Token instead of relying on User Tokens for the leads API, as system tokens do not expire on the same short schedule.
- If the dashboard shows "Meta credentials missing" or "Failed to fetch" errors across multiple pages simultaneously, a token expiry is the most likely cause â€” go directly to Meta Settings to renew.

## 12.7 Troubleshooting Meta Connection Issues

### Symptoms and causes

**All dashboard pages show no data or "Failed to fetch" errors**
- Cause: Token expired, or server is not running.
- Action: Check the server is running on port 4000. Navigate to Meta Settings and check the token expiry date. If expired, follow the renewal process in section 12.6.

**"Cannot connect to server. Please ensure the server is running on port 4000."**
- Cause: The backend server process is not running or is not reachable.
- Action: Restart the server process. Check that port 4000 is not blocked by a firewall or occupied by another process.

**"Please log in to save credentials" (form is disabled)**
- Cause: The JWT authentication token in localStorage is missing or expired.
- Action: Log out and log in again. The dashboard JWT stored under the `app_auth` key in localStorage must be valid before the credentials form can be used.

**"No forms found for this page" (leads section is empty)**
- Cause: The configured token is a single-page-scoped token, or the token lacks `leads_retrieval` permission.
- Action: Configure a System Access Token with `leads_retrieval` permission in the System Access Token field. See section 12.5 for the permanent fix.

**Credentials save succeeds but data still does not appear**
- Cause: New credentials may be cached on the server. The server uses in-memory and database caches for campaigns, ads, and insights with TTLs ranging from 5 minutes to 24 hours.
- Action: Wait 5â€“10 minutes for caches to expire, or trigger a forced refresh if a "Refresh" button is available on the relevant dashboard page.

**401 or 403 response from the server when saving**
- Cause: Dashboard JWT has expired.
- Action: Log out and log back in. Return to Meta Settings and re-save credentials.

**"Meta credentials missing. Please configure META_ACCESS_TOKEN and META_AD_ACCOUNT_ID"**
- Cause: The server environment variables were not loaded from the `.env` file. This error indicates the server-side environment, not the dashboard UI settings.
- Action: Verify the `server/.env` file exists and contains the correct variable names. Restart the server after editing `.env`.

**Token expiry date shows a past date**
- Cause: The stored token has expired.
- Action: Follow the renewal process in section 12.6 immediately.

**Instagram data is missing but ad data shows normally**
- Cause: The token lacks `instagram_manage_insights` or `pages_read_engagement` permissions.
- Action: Generate a new token from the Graph API Explorer with these permissions added. Update the Access Token field and save.

**Campaigns show for some ad accounts but not others**
- Cause: The configured User Token does not have access to all ad accounts you want to monitor.
- Action: Ensure the Facebook user whose token is being used has at least Analyst access on all monitored ad accounts in Meta Ads Manager. Generate a new token from the same user account.

## 12.8 Required Meta API Permissions

When generating an Access Token from the Graph API Explorer, you must request the following permissions. Missing permissions will result in partial data loss silently â€” the API will return reduced data rather than an error in most cases.

### Minimum permissions for the User Access Token

| Permission | Required for |
|---|---|
| `ads_read` | Reading campaign, ad, and insights data from ad accounts |
| `ads_management` | Accessing ad account details and ad account list |
| `pages_read_engagement` | Reading Facebook Page data; required for Instagram account resolution |
| `pages_show_list` | Listing Facebook Pages accessible to the user |
| `leads_retrieval` | Reading leads submitted through lead generation forms (if using User Token for leads) |

### Additional permissions for Instagram data

| Permission | Required for |
|---|---|
| `instagram_manage_insights` | Instagram reach, impressions, engagement, follower demographics |
| `instagram_basic` | Basic Instagram account information and media list |
| `instagram_content_publish` | Not required for the dashboard; do not request unless needed |

### Permissions required specifically for the System Access Token

| Permission | Required for |
|---|---|
| `leads_retrieval` | Fetching leads from lead gen forms via the Page Access Token exchange |
| `pages_manage_metadata` | Required when using per-page token pattern (`META_PAGE_TOKEN_<pageId>`) |

### How to grant permissions in the Graph API Explorer

1. Open [https://developers.facebook.com/tools/explorer](https://developers.facebook.com/tools/explorer).
2. Select your Meta App.
3. Click the "Permissions" section (or the "Add a Permission" button, depending on Explorer version).
4. Search for and tick each permission in the list above.
5. Click "Generate Access Token".
6. Review the permissions dialog and click "Continue as [your name]" then "OK".
7. Copy the resulting token and paste it into the Access Token field on the Meta Settings page.

### System User token (for System Access Token field)

System User tokens are not generated from the Graph API Explorer. They are created in Meta Business Manager:

1. Open Meta Business Manager at [https://business.facebook.com/settings](https://business.facebook.com/settings).
2. Navigate to **Users** > **System Users**.
3. Click "Add" to create a new system user (or select an existing one).
4. Click on the system user, then click "Add Assets" and grant access to the relevant ad accounts and Facebook Pages.
5. Click "Generate New Token".
6. Select your Meta App.
7. Enable the `ads_read`, `leads_retrieval`, and `pages_read_engagement` permissions at minimum.
8. Click "Generate Token" and copy the token immediately (it is shown only once).
9. Paste the token into the "System Access Token" field on the Meta Settings page.

System User tokens do not expire automatically, making them significantly more reliable for production use than short-lived user tokens. For a stable, low-maintenance setup, use a System User token for the System Access Token field and use a long-lived User Token (extended via the token exchange endpoint) for the main Access Token field.

# Section 13: FILTERS & DATA CONTROLS

Filters are the primary means of controlling what data the MHS Marketing Dashboard displays. Every major page exposes one or more filter controls, and understanding how they work together lets you move from a broad overview to a precise slice of data in seconds. This section covers each filter type, how to use it, how filters interact across pages, and what to expect when you reset or revisit the dashboard.

## 13.1 Global Date Range Filter

The Date Range Filter is a modal overlay that appears on every analytics page. It controls the time period for all data displayed on that page. It opens when you click the calendar-icon button in any page's filter bar.

### Opening and closing the filter

Click the calendar-icon button in the top filter bar. A full-screen dimmed overlay appears with the date range modal in the centre. To close without saving any change, click the Cancel button at the bottom of the modal or click anywhere on the dimmed area outside the modal.

### Selecting a preset date range

1. Open the Date Range Filter modal.
2. In the left-hand panel you will see a scrollable radio-button list labelled "Recently used". The 14 available presets are listed there.
3. Click the label of the preset you want. The dual-calendar view on the right immediately updates to highlight the corresponding date range.
4. Click the Update button. The modal closes and the page reloads with the new date range applied.

**Example â€” selecting Last 30 days on June 5 2026:**
Click "Last 30 days". The calendars highlight May 6 through June 4. Click Update. All charts and tables on the page now show data for that 30-day window.

### Complete list of presets

| Preset | What it selects |
|---|---|
| Today | Today's IST date only |
| Yesterday | The previous calendar day |
| Single day | A single date you pick from the calendar (defaults to yesterday) |
| Today and Yesterday | Yesterday through today (2 days) |
| Last 7 days | The 7 complete days before today (e.g., on June 5: May 29 â€“ June 4) |
| Last 14 days | The 14 complete days before today |
| Last 28 days | The 28 complete days before today |
| Last 30 days | The 30 complete days before today |
| This week | Sunday through Saturday of the current calendar week |
| Last week | Sunday through Saturday of the previous calendar week |
| This month | First through last day of the current calendar month |

### Selecting a custom date range

1. Open the Date Range Filter modal.
2. Click any date on either calendar. The preset automatically switches to "Custom" and the clicked date becomes the start date.
3. Click a second date to set the end date. Dates between the start and end are highlighted.
4. If you need to reach a month that is not currently visible, use the month dropdown or year dropdown in the calendar header, or click the left and right arrow buttons to step one month at a time.
5. Click Update to apply.

**Example â€” selecting April 1 to April 15 2026:**
Open the filter. Navigate the left calendar to April 2026 using the month dropdown. Click April 1. Then click April 15. Both dates and all days between them are highlighted. Click Update.

### Selecting a single day

1. Open the Date Range Filter.
2. Click "Single day" in the preset list.
3. Click the desired date on the calendar. The start and end are both set to that one date.
4. Click Update.

### Navigating to a distant month

Each calendar header contains a month dropdown and a year dropdown. Click either dropdown and select directly rather than clicking the arrow buttons repeatedly. The year dropdown spans a 10-year window (2 years back to 7 years forward from today).

### Using the period comparison feature

The Compare feature lets you measure one date range against a prior period side by side.

1. Select your main date range using any preset or the custom calendar.
2. Check the "Compare" checkbox at the bottom of the modal. A second pair of calendars appears below the main calendars.
3. The system automatically pre-fills a comparison period of the same length as your main range, placed immediately before it. For example, if your main range is June 1â€“June 7, the comparison period is pre-filled as May 25â€“May 31.
4. Adjust the comparison calendars if you want a different period.
5. Click Update. Pages that support comparison will display both periods together.

Important: the comparison period must not overlap the main date range at all. If they overlap, the dashboard will show a validation alert and block the Update action until you correct the overlap.

## 13.3 How Filters Affect Data Across Pages

Filters on the MHS Marketing Dashboard are page-scoped, not global. Each page maintains its own independent filter state. Changing a filter on the Ads Analytics Dashboard does not affect the Best Performing Ads page or the Audience Insights page.

### What each filter controls on its page

**Ads Analytics Dashboard**

The Ads Analytics page has two independent filter zones.

The top filter bar (Platform, Time Range, All Projects, Ad Account, Campaign, Ad Name) controls:
- All KPI cards in the Paid Ads section
- All Paid Ads charts
- The Ads Analytics Leads table
- The conversion and spend breakdowns

The Content Marketing filter bar (Time Range, Source, PAGE) is entirely independent. It controls only the Content Marketing KPI cards and charts. Changing the main time range does not affect the Content Marketing section, and vice versa.

The Total Leads section has its own independent Time Range, PAGE, FORM, and PHONE SEARCH filters. These control only the Total Leads table and its count.

**Best Performing Ads page**

The Time Range, All Projects, and Ad Account filters on this page control all ad cards, performance metrics, and ranking tables displayed on the page.

**Best Performing Reels page**

The Time Range, Platform, PAGE, and content-type tabs (All / Posts / Stories / Reels) all affect the same data fetch. Changing any one of them triggers a new data load.

**Audience Insights page**

Time Range, Platform, and PAGE control the audience demographic charts and reach/impression metrics. The Gender dropdown on the Age and Gender Distribution chart only filters that chart's display without reloading data from the server. The Platform Metric 1 and Platform Metric 2 dropdowns on the Platform tab change only which metrics are shown in the platform chart bars.

**AI Insights page**

The date range preset and custom date range at the top of the page control the performance snapshot and drive the lead saturation, creative fatigue, and lead intelligence analyses. The sortable column headers in each table sort the already-loaded results in the browser; they do not re-fetch data.

**Plan / Weekly Targets page**

The week preset buttons (This Week, Last Week, Next Week) and custom date range inputs determine which week's targets and aggregate spend are loaded. They affect all targets and metrics on the page.

**Team Performance Goals page**

The Team dropdown, Platform dropdown, and Week preset all interact: selecting a different team, platform, or week combination triggers a fresh load of goal and performance data.

### Filter dependency chain on the Ads Analytics Dashboard

The Ads Account, Campaign, and Ad Name filters form a strict dependency chain:

- Selecting a project restricts the Ad Account filter to only that project's accounts.
- Changing the Ad Account selection clears the Campaign filter and resets it with campaigns for the new accounts.
- Changing the Campaign selection clears the Ad Name filter and resets it with ads for the new campaigns.

This cascade prevents stale selections (e.g., a campaign from Account A appearing while Account B is selected).

## 13.5 Filter Persistence Between Sessions

Filter states in the MHS Marketing Dashboard are not persisted between browser sessions. When you close the browser tab or log out and log back in, all filters return to their default values for each page.

Within a single session (same tab, navigating between pages), each page retains its own filter state for as long as you remain logged in and do not hard-refresh the page. Navigating away from the Ads Analytics Dashboard and then returning during the same session will generally keep the filters you last set, because the React component state is preserved in memory while the tab is open. However, a full page refresh (pressing F5 or navigating directly to the URL) resets all filters to their defaults.

The one exception is the visual theme. The theme (Light, Dark, Blue, Red, Green, Classic Dark, or System) is saved to your browser's localStorage under the key "theme" and persists across sessions and page reloads.

**Practical advice:** if you run the same recurring report each week, note down your filter combination (date preset, accounts, campaigns) and reapply it each session. The Date Range Filter presets such as "Last week" or "This month" automatically compute the correct dates each time, so you only need to reselect the preset rather than entering specific dates.

## 13.6 Combining Multiple Filters

All filters on a page apply simultaneously. The data shown is the intersection of every active filter â€” it must satisfy every filter condition at once.

### Step-by-step example: narrowing to a specific campaign in a specific period

**Goal:** See ad performance for the "Dental June 2026" campaign during the last 14 days.

1. Open the Ads Analytics Dashboard.
2. Click the date range button. Select "Last 14 days". Click Update. The page loads data for the last 14 complete days.
3. Click the Ad Account filter. Select the ad account that owns the Dental campaign (e.g., "MHS Dental Account"). Click outside to close.
4. Click the Campaign filter. The list now shows only campaigns in the MHS Dental Account. Check "Dental June 2026". Click outside.
5. All KPI cards, charts, and tables now show data for the Dental June 2026 campaign over the last 14 days only.

### Step-by-step example: comparing two platforms in the Audience Insights page

**Goal:** See Facebook audience demographics for the last month.

1. Open the Audience Insights page.
2. Click the Time Range filter. Select "Last month". Click Update.
3. Click the Platform filter. Check "Facebook" only (uncheck any others). Click outside.
4. The PAGE filter appears. If you want data for a specific page, open it and select that page. If you want data across all pages, leave the PAGE filter unselected.
5. The demographic charts update to reflect Facebook audience data for last month.

### Step-by-step example: using Compare with a filtered view

**Goal:** Compare last week's ad spend for one campaign against the week before.

1. Open the Ads Analytics Dashboard.
2. Apply the Campaign filter to select the desired campaign.
3. Click the date range button. Select "Last week". Then check the "Compare" checkbox. The system pre-fills the prior week as the comparison period. Click Update.
4. The dashboard now shows last week's metrics alongside the previous week's metrics for that campaign.

### Tips for combining filters effectively

- Apply the broadest filters first (date range, project, ad account) before narrowing to campaign and ad. This follows the dependency chain and avoids error states.
- On the Ads Analytics Dashboard, the Content Marketing and Total Leads filter bars are independent from the top (Paid Ads) filter bar. You can set different date ranges in each zone on the same page at the same time.
- On the Audience Insights page, the Gender dropdown, Platform Metric 1, and Platform Metric 2 dropdowns change only the chart display without issuing new API calls. Adjust these freely without waiting for a network round-trip.
- If a filter dropdown shows "Loading...", wait for the upstream filter to finish fetching before opening the dependent filter. For example, wait for the Campaign filter to finish loading after you change the Ad Account before opening the Ad Name filter.

## 13.7 Date Format and Timezone Information

### Timezone

All dates and times in the MHS Marketing Dashboard are computed, stored, and displayed in Indian Standard Time (IST), which is UTC+5:30, also written as Asia/Kolkata.

The Date Range Filter displays a static notice in its footer: "Dates are shown in Kolkata Time". This applies to every date shown in the dashboard â€” charts, tables, KPI cards, and exported data.

If you are physically located outside India, the dates you see are still IST dates. For example, a "Today" selection always means the current calendar date in Kolkata, regardless of the local time in your browser's system clock. If it is 11 p.m. in London (UTC+0), "Today" in the dashboard refers to the date in Kolkata, which is already the next calendar day (4:30 a.m. IST).

### Date format

Dates are displayed and entered in YYYY-MM-DD format in filter inputs (for example, 2026-06-05 for June 5 2026). The calendar UI displays day numbers visually, so you do not need to type dates manually in most situations â€” clicking a calendar date is sufficient.

In API-facing fields (such as the AI Insights custom date range and the Plan page's custom date input), dates must be typed in YYYY-MM-DD format. Incorrectly formatted values will be rejected with an error.

### How "Last N days" is counted

"Last N days" presets follow Meta Ads Manager convention: they count complete calendar days and always exclude today.

**Example on June 5 2026:**
- Last 7 days = May 29, May 30, May 31, June 1, June 2, June 3, June 4 (7 days, not including June 5)
- Last 30 days = May 6 through June 4

This means the most recent data point in any "Last N days" view is always yesterday, not today.

### How "This week" and "Last week" are defined

Both presets use a Sunday-to-Saturday week definition.

**Example on June 5 2026 (a Friday):**
- This week = June 1 (Sunday) through June 7 (Saturday)
- Last week = May 25 (Sunday) through May 31 (Saturday)

### The Maximum preset

The Maximum preset starts from January 1 2000 and ends on today. This is the earliest data boundary the system recognises. Selecting Maximum is the equivalent of requesting all historical data.

### Year dropdown range

The year dropdown inside each calendar header is limited to a 10-year window: 2 years before the current year through 7 years after it. As of June 2026, this means you can navigate between 2024 and 2033 using the dropdown. Dates outside this window can only be reached by typing in custom date input fields where available.

### Comparison period and date arithmetic

When the Compare feature calculates a default comparison period, it uses exact day counts. A main range of 7 days produces a comparison range of exactly 7 days immediately before it, with no gap and no overlap. If the main range is 31 days (for example, a calendar month), the comparison period is also 31 days. There is no automatic adjustment for month length in the default calculation; you can manually adjust the comparison calendars after the default is pre-filled.

# SECTION 14: TROUBLESHOOTING GUIDE, FAQ & BEST PRACTICES

---

## 14.1 COMMON ISSUES & SOLUTIONS

---

### Issue 1: "No Data Showing" / Blank Dashboard

**Symptoms:** Dashboard cards are empty, charts render with no data, tables show zero rows, or the entire page appears blank after login.

**Cause A â€” Session not authenticated**
The most common cause is that the browser's localStorage has been cleared or the session token is missing. Every page except /login and /signup is wrapped in a ProtectedRoute. If the `loggedInUser` key is absent from localStorage, the app silently redirects to /login.

Resolution:
1. Log out completely and log back in.
2. If the page still appears blank after login, open the browser's Developer Tools (F12), go to Application > Local Storage, and confirm that both the `ads_dashboard_auth` key and the key defined by `REACT_APP_STORAGE_KEY` (typically `app_auth`) are present with non-empty values.
3. If either key is missing, clear all site data and log in again.

**Cause B â€” Backend server not running**
The dashboard requires the Node.js backend running on port 4000. MetaSettings performs a health check at GET /api/health before loading. If that check fails, the entire page is blocked.

Resolution:
1. Confirm the backend is running. If self-hosted, SSH into the server and verify the process is active.
2. Confirm the server can reach the internet (for Meta API calls) and that no firewall is blocking port 4000.
3. Check server logs for startup errors, particularly missing environment variables.

**Cause C â€” Missing or wrong REACT_APP_API_BASE environment variable**
If `REACT_APP_API_BASE` is not set in the frontend deployment, the Auth pages default to a relative path (/api/auth/login) and AuthProvider defaults to http://localhost:4000. In a split-host deployment (frontend on a CDN, backend on a separate server), this means every API call fails silently.

Resolution:
1. Set `REACT_APP_API_BASE` to the live backend URL (e.g., `https://api.yourdomain.com`) in the frontend build environment.
2. Rebuild and redeploy the frontend. Changes to environment variables are baked in at build time; updating .env alone does not update a deployed build.

**Cause D â€” Permissions not granted**
Non-admin users may have individual pages or sections disabled. If a specific page appears blank for one user but not another, check their permission profile via Settings > Team Management > Manage Permissions.

Resolution:
An admin should navigate to the affected user's permission page and enable the relevant module.

---

### Issue 2: "Failed to Fetch" Errors

**Symptoms:** A red error banner or toast notification reading "Failed to fetch", "Network error", or "ERR_CONNECTION_REFUSED" appears on any dashboard page.

**Root Causes and Resolutions:**

| Root Cause | How to Identify | Resolution |
|---|---|---|
| Backend server is down | Error appears on all pages simultaneously | Restart the backend server; check for crash logs |
| REACT_APP_API_BASE points to wrong URL | Error appears immediately after login | Correct the environment variable and rebuild |
| CORS misconfiguration | Error visible in browser console as a CORS policy block | Update server CORS settings to allow the frontend origin |
| Meta API credentials not configured | Error only on Ads/Leads pages | Add META_ACCESS_TOKEN and META_AD_ACCOUNT_ID to server/.env |
| Network timeout | Error appears after a long wait (20â€“30 seconds) | Check server performance; Meta API may be slow; try again |
| Wix credentials missing | Error only on Wix analytics section | Add WIX_SITE_ID and WIX_TOKEN to server/.env and restart |

**General Resolution Steps:**
1. Open the browser console (F12 > Console tab) and read the full error message, including the URL it was attempting to reach.
2. Confirm the URL matches the expected backend address.
3. Try navigating to the backend health endpoint directly in the browser: `[your-backend-url]/api/health`. If that returns an error, the backend itself is the problem, not the frontend.
4. If the fetch is to a Meta endpoint, verify the META_ACCESS_TOKEN in server/.env is valid and not expired.

---

### Issue 3: Meta Token Expired â€” What to See and What to Do

**What you will see when the token has expired:**

- Lead tables on the main dashboard display a permission or authentication error message with instructions to regenerate the token.
- The Best Performing Ads page shows an error banner and no data loads.
- The AI Insights page loads from cache on first visit but the Refresh button fails.
- The Audience page displays "token invalid" in the Followers card.
- The Best Performing Reel page shows a timeout or permission error for media fetches.
- MetaSettings will show a token expiry date on its status banner â€” if this date is in the past, the token has expired.

**Why this happens:**
The User Access Token issued by Meta Graph API Explorer expires approximately every 90 days. The dashboard does not auto-renew tokens.

**Step-by-step resolution:**

1. Go to [Meta Graph API Explorer](https://developers.facebook.com/tools/explorer/).
2. Select your App from the dropdown.
3. Click "Generate Access Token."
4. In the permissions selector, ensure `leads_retrieval`, `ads_read`, `pages_read_engagement`, `instagram_basic`, and `instagram_manage_insights` are included.
5. Copy the generated token.
6. In the dashboard, navigate to Settings > Meta Settings.
7. Paste the new token into the Access Token field. Also update the System Access Token field with a token that has `leads_retrieval` permission (see note below).
8. Click Save. The sensitive fields will be cleared from the form after saving â€” this is expected and confirms the save was successful.
9. Navigate to the main dashboard and click "Refresh with live data" to confirm data is loading.

**Important note on System Access Token vs User Access Token:**
The `leads_retrieval` permission requires a System Access Token (not a User Access Token) for reliable access to lead forms across all pages. If you enter only a User Access Token and leave the System Access Token blank, lead forms may return "No forms found for this page" â€” especially for pages where your user account is not the primary owner. Always configure a System Access Token for production use.

### Issue 4: "No Forms Found for This Page" Error

**Symptoms:** The leads section for a specific Meta page shows "No forms found for this page" even though lead forms exist in Meta Business Manager for that page.

**Root Cause:**
This is the most common recurring configuration issue in the MHS dashboard. It occurs because:

- The User Access Token (set in the Access Token field of Meta Settings) is a single-page token that only has `leads_retrieval` access for one specific page â€” not all pages.
- A User Access Token expires after approximately 90 days, after which all lead form fetches fail.
- The System Access Token field in Meta Settings was left blank, so the dashboard cannot fall back to a broader-scope token.

**Permanent Resolution:**

1. In Meta Business Manager, create a System User under Business Settings > System Users.
2. Assign the System User Admin or Employee level access.
3. Generate a System User Access Token and check the `leads_retrieval` permission.
4. System User tokens do not expire (unless manually revoked), making this the reliable long-term solution.
5. In the dashboard, navigate to Settings > Meta Settings and enter this token in the System Access Token field.
6. Save. From this point, lead forms for all connected pages will be accessible.

**Temporary workaround (if System User access is not immediately available):**
Generate a Page Access Token (not a User Access Token) specifically for the page in question via Graph API Explorer. Page Access Tokens scoped to `leads_retrieval` can access forms for that specific page and do not expire.

### Issue 5: Slow Loading / Performance Issues

**Symptoms:** Dashboard takes more than 10 seconds to load, charts appear with a long delay, or the page shows a spinner for an extended period.

**Common Causes and Resolutions:**

**Cause A â€” Live Meta API fetch instead of cache**
Clicking "Refresh with live data" forces a direct Meta API call including video metrics (Hook Rate, Hold Rate). This call is significantly slower than loading from the database cache. The Best Performing Reel page has a 45-second hard timeout for media insights.

Resolution: For routine viewing, do not click "Refresh with live data" on every page load. Use cached data (the default) for daily monitoring and reserve live refreshes for reporting runs.

**Cause B â€” Large date range on Wix analytics**
Wix stores analytics data for a maximum of 62 days. Requesting a date range beyond 62 days returns a 400 error. Even within the limit, large ranges are slower.

Resolution: Keep Wix date ranges to 30 days or fewer for best performance.

**Cause C â€” AI Insights page timeout**
The Ask AI feature has a 120-second timeout (longer than other API calls). If the Gemini AI backend is under load, the request will approach this timeout.

Resolution: If the spinner runs for more than 90 seconds, the request has likely stalled. Click away and return to the page. Verify the backend API server is running. If a Gemini quota countdown banner appears, wait for the timer to expire before retrying.

**Cause D â€” Many active ads or large Meta account**
The Best Performing Ads and Best Performing Reel pages fetch live data from Meta. Accounts with many campaigns, ads, or media posts will take longer to load because the Meta API must paginate through more records.

Resolution: Narrow the date range to 7 days or fewer when checking performance. The charts display a maximum of 20 ads regardless of how many are fetched.

**Cause E â€” Backend server under-resourced**
If the server is running on a low-memory instance or has not been restarted recently, memory pressure can slow all API responses.

Resolution: Restart the Node.js server. Monitor server memory and CPU during peak usage.

### Issue 6: Login Issues

**Symptom A â€” "Login failed: no token received" error message**

This error means the backend returned an HTTP 200 response but the JSON body did not include a `token` field. This indicates a backend misconfiguration, not a wrong password.

Resolution:
1. Check backend logs for errors during the login handler.
2. Confirm the database connection is healthy and the user record exists.
3. If the backend recently had environment changes, restart the server.

**Symptom B â€” Correct credentials rejected with "Invalid credentials" or similar**

Resolution:
1. Confirm Caps Lock is off.
2. Try the exact email address used at signup (case-sensitive on some backends).
3. If credentials are genuinely unknown, there is no self-service "Forgot Password" feature in the current implementation. Contact your dashboard administrator to have the password reset manually in the database.

**Symptom C â€” Immediately redirected back to /login after logging in**

This happens when the localStorage write fails (for example, the browser is in private/incognito mode with storage disabled, or the site's storage quota is exhausted).

Resolution:
1. Try a standard (non-incognito) browser window.
2. Clear the site's localStorage (F12 > Application > Local Storage > right-click the domain > Clear) and log in again.
3. If the issue persists in a standard window, check browser settings for site-specific storage restrictions.

**Symptom D â€” Session expires mid-session (auto-redirected to /login while working)**

The client-side session is stored in localStorage and does not have a client-enforced expiry timer. However, if the server returns HTTP 401 on any data fetch (because the server-side token has been invalidated or the server was restarted with a new JWT secret), the application will redirect to /login.

Resolution:
1. Log in again. Your data is not lost.
2. If this happens frequently, check whether the JWT secret is being regenerated on each server restart (it should be stored as a fixed environment variable, not generated dynamically).

**No "Forgot Password" Self-Service:**
The current implementation does not include a password-reset or forgot-password flow. Users who lose their password must contact an administrator. Administrators must reset passwords directly in the database or via a backend utility.

### Issue 7: Leads Not Syncing

**Symptoms:** Lead count in the dashboard does not match what is visible in Meta Lead Center; new leads submitted hours ago do not appear in the leads table.

**Understanding the sync architecture:**
The leads table reads from the local Supabase database. A background job syncs this database with Meta every 15 minutes automatically. The "Sync All Leads" button on the main dashboard triggers an immediate on-demand sync outside the scheduled window.

**Resolution Steps:**

1. Click the "Sync All Leads" button on the main dashboard and wait for the sync to complete (it will show a success or error notification).
2. If a specific page's form shows a "Sync issue" badge (meaning Meta reports leads for this form but the database count is zero), the page's Meta access needs reconnecting. This is almost always caused by an expired User Access Token or a missing System Access Token for that page.
3. Follow the Meta Token resolution steps in Issue 3 above to refresh the token.
4. After updating the token, run Sync All Leads again.
5. If leads are still missing after a successful sync, confirm the lead form ID in Meta Business Manager matches what the dashboard is querying. Form IDs can change if a form is duplicated or recreated.

**Important caveat on campaign/ad attribution:**
Meta's Graph API does not provide campaign or ad attribution per individual lead. The Campaign and Ad Name columns in the Total Leads Admin View reflect the filter context that was active when the leads were loaded â€” they are not direct per-lead attribution data pulled from Meta.

### Issue 8: Charts Not Rendering

**Symptoms:** A chart area appears blank, shows "No data available," or the chart container is visible but contains no visual content.

**Cause A â€” No data for the selected date range**
The most common cause is that the selected date range returns zero records for the metric being charted.

Resolution: Widen the date range. Confirm that the correct Platform and Page filters are selected. For the Audience page, the PAGE filter only appears when Facebook or Instagram is specifically selected â€” if "All Platforms" is selected, page-specific charts will not render.

**Cause B â€” Best Performing Reel â€” Subscriber Change chart shows placeholder data**
If the Meta API does not return a `daily_subscriber_change` data series, the chart renders with sample placeholder data showing a Novâ€“Dec date range. This is a known limitation and does not indicate a system error.

Resolution: This is expected behaviour. No action is required. The chart will show real data when Meta provides the series.

**Cause C â€” Platform tab chart shows static placeholder data**
In the Audience page, the Platform tab chart uses static placeholder data in the current version. A note at the bottom of that section confirms this. It does not indicate a configuration problem.

**Cause D â€” framer-motion library missing (High-Five Landing page)**
The /high-five route depends on the framer-motion library. If this package is missing from the frontend build, that page will fail to render entirely.

Resolution: Run `npm install framer-motion` in the client directory and rebuild.

**Cause E â€” Wix date range exceeds 62 days**
Wix analytics requests for date ranges beyond 62 days return a 400 error, which causes the associated charts to render empty.

Resolution: Select a date range of 62 days or fewer.

## 14.2 FREQUENTLY ASKED QUESTIONS

---

**Q1: How often is data refreshed?**

Different data sources refresh on different schedules:

| Data Source | Refresh Frequency | Trigger |
|---|---|---|
| Meta Ads (dashboard) | Loaded from database cache on page load | Live refresh: manual "Refresh with live data" button |
| Meta Leads | Every 15 minutes automatically | On-demand: "Sync All Leads" button |
| Revenue / Google Sheets KPIs | Every 30 seconds (polled) | Automatic; no manual trigger needed |
| Wix Analytics | On page load with selected date range | Manual: change date range and reload |
| AI Insights (Saturation, Fatigue, Lead Scoring) | On page load (reads from cache) | Manual: "Re-run" or "Run Scoring" buttons per section |
| Home page stat cards | Static (hardcoded) | Not dynamic in current version |

**Q2: Why are my leads showing duplicates?**

Duplicate leads in the dashboard table most commonly occur when:

- The same lead submitter filled out the same form twice (Meta allows this).
- A sync was triggered multiple times during a period when the deduplication logic encountered a database constraint issue.

The leads sync service is designed to be idempotent. If you are seeing duplicates, export the leads table and filter by phone number to identify repeated entries. Report the lead form ID and date range to the system administrator so the database can be reviewed. Do not manually delete records without confirming with the administrator, as this may affect revenue reconciliation.

**Q3: Can I export all data?**

Yes, with the following scope:

- **Lead Intelligence Scoring (AI Insights page):** The Download button exports all scored leads as a CSV or XLSX file. Note that the on-screen table shows only the top 50 rows, but the export contains the complete dataset.
- **Other dashboard data:** There is no bulk "export everything" function. Individual sections (leads tables, ad performance tables) may provide their own export options depending on your permission level.
- **Data limits:** Wix analytics data is only available for the last 62 days. Meta Ads data availability depends on your Meta account's data retention settings. Historical data beyond the retention window is not retrievable.

**Q4: How do I add a new team member?**

Only administrators can add new users. Steps:

1. Navigate to Settings > Team Management.
2. Click Add New Member.
3. Fill in the email address, assign a role (Admin or Restricted), and set a temporary password.
4. Click Save.
5. Share the credentials with the new team member.
6. If the new member needs access to specific dashboard sections, navigate to their record, click Manage Permissions, and enable the relevant modules.
7. Instruct the new member to change their password on first login (via the Edit User flow â€” filling in the password field updates it; leaving it blank preserves the existing one).

**Q5: How do I connect a new Meta ad account?**

1. Navigate to Settings > Meta Settings.
2. Enter the Ad Account ID in the format `act_XXXXXXXXX` (the `act_` prefix is required).
3. Ensure the Access Token entered has permissions to read this ad account's data (`ads_read` permission).
4. Enter the App ID and App Secret for the associated Meta App.
5. If the new account has lead generation pages, also update the System Access Token with `leads_retrieval` permission.
6. Click Save.
7. Navigate to the Best Performing Ads page. If credentials are valid, data for the new account will begin loading.

Note: Only active campaigns and ads are shown. Paused, archived, or deleted campaigns are filtered out automatically.

**Q6: What do I do if my Meta token expires?**

See the detailed resolution in Issue 3 (Meta Token Expired) in Section 14.1. The short version:

1. Go to Meta Graph API Explorer.
2. Generate a new User Access Token with the required permissions.
3. Go to Settings > Meta Settings and update both the Access Token and, ideally, the System Access Token fields.
4. Save and verify data is loading.

Proactive recommendation: Set a recurring calendar reminder for 80 days after each token update to renew it before expiry. The MetaSettings page displays the token's expiry date â€” check it regularly.

**Q7: How far back does historical data go?**

| Data Type | Historical Availability |
|---|---|
| Meta Ads performance data | Subject to Meta's data retention (typically 36 months for campaign data, shorter for some breakdowns) |
| Meta Leads | From the date the lead sync was first configured for each form |
| Wix Analytics | Maximum 62 days from today |
| Google Sheets revenue data | As far back as the sheet itself contains records |
| AI Insights performance snapshots (Today / Last 7 / 14 / 30 days) | Rolling windows relative to current date â€” not configurable to arbitrary historical dates |

For audit or reporting purposes beyond these windows, data must be sourced from Meta Business Manager's native export tools or from the raw Google Sheets documents.

**Q8: Can multiple users be logged in simultaneously?**

Yes. The dashboard supports concurrent sessions for multiple users. Each user's session is independent and stored in their own browser's localStorage. One user logging out does not affect another user's session.

However, be aware of the following:

- **Permission changes take effect immediately.** If an admin changes a user's permissions while that user is actively using the dashboard, the restriction will apply on the user's next data fetch or page navigation, not instantly.
- **Meta Settings changes are global.** If one user updates the Meta access token in Settings > Meta Settings, the new token is used by all subsequent API calls from all users. This is intentional â€” token configuration is a server-level setting, not per-user.
- **Plan targets are shared.** Team targets set in the Plan page are stored in the backend database and are therefore visible and editable by all users with access to that page. Coordinate with your team before making changes.

## 14.3 BEST PRACTICES

---

### 14.3.1 Daily Dashboard Review Routine

A consistent daily review ensures you catch performance issues early and have context for data anomalies when they occur.

**Recommended morning routine (10â€“15 minutes):**

1. **Check the main dashboard first.** Open the Dashboards page. Review the Ads Analytics KPI cards (Impressions, Clicks, CTR, Leads, CPL) for the last 7 days with "today minus 6 days through today" as your default range.
2. **Check the campaign saturation banner.** If the banner at the top of the dashboard shows saturated campaign names, open AI Insights and review the Saturation Index section before making budget decisions for the day.
3. **Verify lead sync.** Confirm the Total Leads count has updated since the previous day. If the lead count has not moved since yesterday, click "Sync All Leads" and check for any "Sync issue" badges on individual forms.
4. **Review revenue KPIs.** The Online Conversion, Offline Conversion, and Total Revenue cards in the Ads Analytics section update from Google Sheets every 30 seconds. Confirm these are reflecting current data.
5. **Check the Hot Leads queue (AI Insights).** Open the Lead Intelligence Scoring table and filter to "Hot" tier. Hot leads require a personal call within 2 hours â€” ensure these are being actioned promptly.

**Recommended weekly review (30â€“45 minutes, recommended on Mondays):**

1. Change the date range to the previous full week (Monday to Sunday).
2. Review the Best Performing Ads page for top spend, CTR, ROAS, and conversion counts across campaigns.
3. Review the Best Performing Reel page for Hook Rate and engagement across content.
4. Run the AI Insights Creative Fatigue analysis. Any ads scoring above 70 (Fatigued) should be flagged for creative refresh.
5. Review the Plan page and update team targets if the current week's goals have changed.
6. Export Lead Intelligence Scoring for weekly reporting.

---

### 14.3.2 Setting Up Proper Date Ranges for Reporting

Different sections of the dashboard use different date range defaults. Standardising your approach avoids comparing mismatched windows.

**Rules to follow:**

- **Ads Analytics default:** Last 7 days (today minus 6 days through today). This is the system default and is suitable for weekly performance reviews.
- **Content Marketing default:** Last 7 complete days (yesterday minus 6 days through yesterday). This is one day behind the ads range because today's data may be incomplete. The system uses this default automatically â€” do not override it to include today unless you specifically want partial-day data.
- **Unfollows card:** Always shows the last 28 days regardless of your selected range. This is a Meta API fixed window and cannot be changed. Do not attempt to interpret this card in the context of a shorter date range.
- **Wix Analytics:** Never select more than 62 days. The API returns a 400 error beyond this limit, which will break that section's charts. For month-over-month comparisons, run two separate 30-day queries.
- **AI Insights Performance Snapshot tabs:** These use rolling calendar windows (Today, Last 7 days, Last 14 days, Last 30 days) relative to the current date. They do not respond to the hero date range picker. Use these for trend context, not for precise custom-period reporting.
- **For formal reports:** Use a consistent Monday-to-Sunday or calendar-month window across all sections. Set each section's filter manually â€” do not assume all sections are showing the same period.

---

### 14.3.3 Monitoring AI Insights Regularly

The AI Insights page provides three analytical outputs that are most valuable when reviewed on a regular cadence:

**Lead Saturation Index (review weekly):**
The saturation threshold for action is:
- Above 60 (Yellow/Warning): Begin planning creative refresh and audience expansion.
- Above 80 (Red/Critical): Pause the campaign or significantly reduce budget until new creatives are in rotation. First-time impression share below 30% alongside a red saturation score confirms audience exhaustion.

Do not wait for the saturation banner on the main dashboard â€” run the full Saturation Index analysis in AI Insights for a campaign-level breakdown.

**Creative Fatigue Score (review every 2 weeks per active ad):**
Score bands: Fresh (0â€“40), Aging (40â€“70), Fatigued (70â€“100), Severe (100+). Any ad scoring Fatigued or Severe should be replaced. Do not continue spending on Severe-rated creatives â€” the formula accounts for CTR drop, lifespan pressure, and hook drop rate, meaning spend on these ads is likely wasted.

**Lead Intelligence Scoring (review daily for Hot leads, weekly for all tiers):**
The MHS Sugar scoring model assigns leads to tiers with defined action windows:
- Hot (80+): Personal call within 2 hours.
- Warm (50â€“79): WhatsApp sequence within 24 hours.
- Nurture (25â€“49): Follow-up sequence within 48 hours.
- Cold (0â€“24): Weekly broadcast only.

Missing the Hot lead window is the highest-cost inaction in the system. Make Hot lead review the first step in every morning's dashboard check.

---

### 14.3.4 Token Renewal Schedule

Meta User Access Tokens expire approximately every 90 days. Missing this window causes all Meta-dependent features to fail simultaneously. Proactive renewal is the single most important operational maintenance task for this dashboard.

**Recommended schedule:**

| Action | Timing | Who |
|---|---|---|
| Check token expiry date in Meta Settings | Weekly (every Monday) | Dashboard administrator |
| Set calendar reminder at time of each token update | Day of update, for 80 days later | Dashboard administrator |
| Generate and update new token | At the 80-day mark (10 days before expiry) | Dashboard administrator |
| Verify all sections loading after update | Same day as renewal | Dashboard administrator |
| Update System Access Token | Same day as User Token renewal | Dashboard administrator |

**Important:** A System User Access Token (generated through Meta Business Manager > System Users) does not expire as long as it is not manually revoked. Migrating to a System User token for both the Access Token and System Access Token fields eliminates the 90-day renewal cycle entirely for production deployments. See Issue 4 in Section 14.1 for setup instructions.

---

### 14.3.5 Data Backup Recommendations

The MHS Marketing Dashboard is a read/display layer over several external data sources. However, the following data is stored in your local Supabase database and should be backed up independently:

**What to back up:**

- **Leads database:** The Supabase `leads` table is the authoritative source for conversion tracking. Meta's own lead storage is not a reliable long-term archive. Export the leads table monthly to a secure spreadsheet or CSV, particularly before making any schema migrations.
- **Plan targets:** Team targets stored via /api/plan/targets are in the database. Before running any server migration scripts, export the plan_teams data.
- **User accounts and permissions:** Back up the users and permissions tables before any Team Management bulk changes.
- **Google Sheets revenue data:** Ensure the Google Sheets documents used for revenue data have edit history and sharing settings that prevent accidental deletion. These sheets are external to the dashboard and must be managed separately.

**What NOT to store in the dashboard database:**
Raw phone numbers must never be stored in analytics systems. The Collaboration module documentation specifies that only SHA-256 hashed phone numbers may be stored. Ensure any data pipeline feeding the leads table respects this requirement.

**Backup frequency recommendation:**
- Leads table: Export weekly (every Sunday or Monday morning, before the weekly review).
- Plan targets: Export before each new monthly planning cycle.
- User/permissions data: Export before any Team Management changes.
